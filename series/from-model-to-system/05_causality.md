# 第五期 因果与实验 怎样找到有效的改变

[返回系列目录](README.md)

## 难的是下一步改哪里

系统答错了，原因通常不难想：图片没读清，检索没找到材料，规则写得太宽，模型漏掉了某个例外。难的是接下来那一步。这几种解释都对得上眼前的现象，我们却只能挑一部分去改；改完以后跑对了，也说不清上一次到底错在哪。

能自己改写提示词、规则和程序的 Agent，让这件事更突出。它很容易写出一段通顺的失败分析，再给出一份新方案；可分析准不准、方案为什么有效，需要另一套证据。

上一篇问的是：一个结论凭什么成立。这一篇往前走一步：准备动系统的时候，凭什么相信这个改动有效？问题从“这个答案可信吗”，变成了“如果改这里，会发生什么”。

## 两个错误，一个正确答案

先看一个故意构造的小例子。任务是从材料里读出金额，再乘以业务规定的系数。材料上写的是 80，正确系数是 1，正确结果就是 80。旧系统把金额读成了 100，又用错了系数 0.8，最后输出的还是 80。

只看最终答案，这个案例是对的。现在把读取和系数分别修好，一共得到四种组合：

| 读取结果 | 旧系数 0.8 | 修正系数 1 |
| --- | ---: | ---: |
| 旧读取 100 | 80 碰巧正确 | 100 错误 |
| 修正读取 80 | 64 错误 | 80 正确 |

只修读取，结果从对变错。只修系数，也是错。两处一起修，才回到正确的机制。这些数字是为推导编的，不是哪次实验的统计，但它们揭示的结构是真实的：两个错误可以相互抵消，修好一个部件，可能正好把另一个部件的问题暴露出来。

于是两个常见的判断都靠不住。“这个案例原来是对的”，不能证明原来的每一步都该保留；“这个改动让分数掉了”，也不能证明改动里的每一项都错了。最终指标衡量系统交付了什么；要决定下一步改哪里，还得知道结果是怎么来的。

真实系统里的抵消，很少像乘法这么显眼。一条证据被读弱了，恰好碰上一条过宽的规则；检索器漏掉了关键段落，生成器凭已有知识猜对了答案；一条判断路径有漏洞，另一条冗余路径给出了正确输出。系统看上去很稳，输入稍微一变，几处问题会一起冒出来。

所以归因不能停在“找到一个讲得通的原因”。旧系统输出 80 的时候，“读取和系数都没问题”也讲得通，可它是错的。

> 一个解释值不值得信，要看它能不能做出预测：如果它是真的，改动哪里，会看到什么。

能做出这种预测的解释，才能进入实验，实验结果才能帮我们选下一步。

## 四种“为什么”

工程讨论里的“为什么”，常常混着四种不同的问题。某个字段和错误经常一起出现，这是统计关联。一条规则需要哪些前提，这是逻辑依赖。改了某个模块以后输出变了，这是软件里的干预效果。顾客实际怎样使用商品、某个事件有没有造成损坏，这是现实世界的因果。

它们能互相提供线索，但不能互相顶替。比如，长请求更容易失败。可能是长度本身加重了处理负担，也可能是复杂的请求本来就更长、更难。从日志里挑出长请求，会把这些相关特征一起挑进来。拿同一个请求，只改其中一部分，再看系统怎么反应，问的才是一个明确的干预问题。

Pearl 对因果推断的核心区分，就是从观测数据里的关联，转到改变条件之后会发生什么。回答干预和反事实问题，要讲明关于生成机制的假设，相关性不会自动给出答案。[Pearl，2010](https://ftp.cs.ucla.edu/pub/stat_ser/r354-reprint-corrected.pdf)

软件给了我们现实世界少有的便利：一部分机制是自己写的，一部分状态可以保存，一部分输入可以精确替换。开头的例子就是这样：把读取固定在 100，只把系数换成 1，得到 100。这个数不用猜，可以直接算出来。规则引擎也一样：只要输出完全由记录里的事实和规则版本决定，冻结其他条件、只改一个事实，就能算出这次替换的影响。

但要清楚它回答的是哪个问题。设程序把“衣身存在破洞”当作一项输入，把它从真改成假，结论跟着变了。这说明这项事实参与了当前程序的判断。它不说明现实中的破洞是谁造成的，也不说明这项事实当初读得对不对：前一个问题要现实证据，后一个问题要回头核对观察过程。

概念瓶颈模型的研究也做了同样的区分：修改模型预测出的中间概念，看最终预测怎样变化；在现实中改变相应的概念，看现实结果是否变化。两者干预的是不同的对象。[Koh 等，2020，第 2 节](https://proceedings.mlr.press/v119/koh20a/koh20a.pdf)

界线说清楚了，程序里的反事实反而更好用：它专门定位计算链路里的依赖和敏感点，回答“一项假设变了，这个系统会怎样重新计算”。现实里的因果，交给相应的观察、实验或识别条件。

## 把“模型没理解”拆开

看到一个错案，最先冒出来的往往是最熟悉的解释。一直在改提示词的人先怀疑提示词，维护规则的人先怀疑规则，管数据的人先怀疑样本质量。要跳出各自的习惯，就得把解释写成能做出不同预测的假设。

开头的例子可以这样拆。“只有读取错了”预测：换上核对过的 80、系数不动，结果会恢复正确。实际得到 64，这个假设被排除。“只有系数错了”预测：系数改回 1 就对，实际得到 100，同样被排除。剩下“两处都错”，由右下角那一格来验证。

换到多模态判断上，结构也一样。系统认为衣身破损，回头看原图，孔洞其实在吊牌上。至少有三种可能：观察模型认错了对象；观察结果分清了对象，但中间接口没有保存归属；归属保存了，执行规则时却把不同对象的属性拼到了一起。三者产生同一个最终错误，修法各不相同，检查也各不相同。

怀疑观察，就把核对过的对象身份放进原接口，规则不动，看结论是否恢复。怀疑接口，就看原始回执里是否已经有对象信息，后面的状态还能不能表达它。怀疑规则，就喂给它一份明确区分对象的输入，直接看它是否仍然跨对象组合。

“模型没理解”太宽，任何结果都能被它解释；“对象身份在提取回执里是对的，合并时丢了”则指出了具体的差异位置，可以比较合并前后的状态，也可以构造只交换对象归属、其余不变的材料。假设越具体，要查的范围越清楚。

具体不等于互斥。一个系统可以既读错了，又规则过宽，100 和 0.8 就是同时存在的两个错误。修了读取，规则问题还在；单独收紧规则，又可能把读取错误掩盖起来。诊断要容得下共同作用，不能硬把每个失败塞进一个类别。

还有两个问题要分开：“这个信息如果是对的，会怎样”，和“我们能不能稳定地拿到对的信息”。手工把 100 换成 80，证明的是读取值得修，也能估计修好以后的收益上限；它没有证明换一段提示词，模型就能稳定读出 80。前者是诊断实验，后者要用真实的读取过程来检验。

同理，把输出直接改成参考答案，当前案例一定能修好，却什么机制也没解释。有用的候选要落到能重复执行、能拿到新材料上检查的变化：改了哪个问题，加了哪次观察，补上了哪种关系，缩小了哪条规则的范围。

## 同一份材料，跑四遍

要比较改动，先定实验单位。对一个两阶段系统，可以把每份固定的材料当作一个单位，观察版本记为 O0、O1，规则版本记为 R0、R1，每份材料都把四个组合跑一遍，保存各自的中间状态和输出。开头那张表，就是一份材料的四格：读取对应观察，系数对应规则。

四格的价值来自同一份材料上的配对比较。O0R0 和 O1R0 比的是旧规则下改观察的效果，O0R1 和 O1R1 比的是新规则下同一改动的效果。确定性回放里，两个效果不一样，就说明观察改动起多大作用，取决于规则是什么；反过来比较规则也一样。

把事先约定的质量指标记为 q，四格的值记为 q00、q10、q01、q11（第一位是观察版本，第二位是规则版本），加法尺度上的交互可以写成：

```math
I = (q_{11}-q_{01})-(q_{10}-q_{00})
```

它比的是“新规则下改观察的收益”和“旧规则下改观察的收益”。开头的例子按最终答案对错记为 1 或 0，四个值依次是 1、0、0、1，交互量为 2。这表示在“对或错”这把尺子上，两项改动有很强的交互，不是说它们带来了百分之二百的业务收益。换一把尺子，比如绝对误差，四个值是 0、16、20、0，交互量变成 −36，数值和解读方式都跟着变了。

所以，面对两项改动的联合改善，通常没有一个脱离评价方式和比较顺序的“贡献百分比”。在开头的例子里，修读取在旧系数下让对错得分降了 1，在新系数下升了 1，问它“贡献了多少”，得先说是在哪个系数下。可以规定一种分配办法，也可以分别报告各条件下的边际效果，但要写明。先回答“改动在什么条件下有效”，比急着把收益分给各个模块更有用。

冻结条件要足够具体。只固定案例编号不够，原始材料、规则版本、工具返回、阈值和上下文都可能改变结果。模型有随机性时，保存的那次原始回执只适合分析那一次轨迹；要判断稳定的效果或交互，就得多次运行或用足够多的新案例，并报告波动。

混合版本之间还要有说得清的接口。如果新观察把“破损”拆成三个概念，旧规则只接受一个布尔值，O1R0 就不是天然定义好的实验。我们得说明怎样转换，转换时丢没丢信息。否则测到的差异，可能主要来自兼容层，而不是想比较的观察方法。

检索问答系统也能这样拆。保存新旧检索器各自返回的文档，再让新旧提示词分别消费这两份结果。这样就能分开三个问题：新证据本身有没有帮助，生成器会不会用已有的证据，两个改动是不是必须一起出现。所有模块一起换掉、只留最终分数，这三个问题就都无从比较。

## 节点更好，不等于 Agent 更好

对会根据中间结果继续行动的 Agent，还要分清局部回放和完整运行。换一个提示词，它可能选另一个工具；工具返回的材料不同，后面的轨迹也跟着变。如果把后续输入全部冻结，我们隔离出了某个节点的处理差异，也切断了新策略本来可能拿到的收益。这种实验适合解释局部机制，代替不了完整策略的验收。

可行的顺序是：先用局部替换确认一条错误路径，再让候选从相同的起点完整跑一遍，看它是否真的按预期拿到信息、完成任务。前者控制的变量多，后者保留了行动之间的反馈。写清两者各自回答什么，就不会把“这个节点在相同证据下更好”误写成“整个 Agent 已经稳定更好”。

完整运行的结果波动大时，还要看变化是否集中在某几条分支上。平均分差不多，可能是一条路径变好、另一条变坏；把结果对回经过的操作和适用条件，才能决定下一轮是缩小修复范围，还是继续换策略。

## 不变，不等于不重要

开头的例子里，只改一处，结果变坏了，但那一处并没有改错。还有反过来的情况：只改一处，结果没变，也不代表那一处不重要。不变，可能是因为另一条支撑路径还在。

看一条简化规则：“存在结构损伤”或“承诺不符”，只要有一项成立，就可以进入某种处理。先把两件事说定：输出只表示“当前前提是否足以推出这一处理”；“撤销”一项事实，只表示不再把它当作可用前提，不等于判它为假。

现在两项都成立。单独撤销结构损伤，承诺不符仍然支持结论；单独撤销承诺不符，结构损伤也仍然支持结论。两项一起撤销，当前的前提就推不出这一处理了，但这并不证明相反的处理才对。

所以单个事实的边际效果为零，不说明它不能独立支撑结论。要看的是支撑集合：哪些事实一起被拿掉，结论就推不出来了。如果一个撤销集合能造成这种变化，而它的任何真子集都不能，就叫它最小撤销集合。这是当前规则、当前输入下的一个逻辑性质。

“最小”按的是集合包含关系，不一定元素最少，更不一定代价最低：一项观察很便宜，另一项要重新联系外部来源，同样只涉及一个字段，成本可能差很多。逻辑分析给出候选，工程决策还要算上能不能做、花多少。

随意翻转字段，还可能造出不可能的状态。比如一个对象被标成“没出现”，却又有经过确认的局部细节；某个数值和由它算出的类别互相矛盾。这种输入能测程序的防御能力，却不是合理的现实反事实；研究真正可能发生的修改，要保持对象关系、派生约束和证据范围一致。

这让“生成反例”成了一件需要领域结构的事。每次构造，都要说明改了什么、哪些条件不动。查关键因素时，固定对象身份，只改衣身有没有孔的证据，看规则是否跟着响应；查无关因素时，衣身证据不动，改吊牌的状态，或者只调换图片顺序，看结论会不会无故变化。前一种检查系统有没有响应该关心的变化，后一种检查它有没有被不该关心的变化带偏。

这些检查覆盖不了所有可能的输入，结果符合预期，也只是增加了对某个机制解释的支持。它们的力量来自针对性：每一次改动都有理由，每一次输出变化都能对回正在检验的假设。

## 修好熟悉的，再看没见过的

一个解释能说明已有的错误，还要经得起没参与构造它的材料。最容易过度乐观的时候，是候选在几个熟悉案例上全部奏效的时候。这些案例已经被反复看过，规则很可能悄悄贴合了它们的细节。

所以修复的验收要用两类材料。一类是针对机制构造的边界案例，看规则是否真的守住了它声称的区别；另一类是留出来的新材料，看这个区别在更广的分布上有没有用。前者帮助解释，后者估计能迁移多少效果，两者不能互相顶替。

比如把“有孔即破损”这条规则收紧，可能修好了吊牌误判，却漏掉了一些真实的衣身孔洞。看影响范围时，要同时看三类案例：被修好的错误，原来正确、现在变了的案例，以及仍然失败的案例。只展示成功翻转的那部分，就丢掉了决定这次修法能不能采用的信息。

修复还可能改变资源的用法。加一次定向读取，能提高某类边界情况的判断质量；可如果每个案例都触发同样的读取，成本可能很高。原因找得准、适用范围划得清，额外的操作就可以只发生在需要的地方。归因因此也决定了计算和观察的预算花在哪里。

候选被拒绝时，反馈也要具体。回到开头的例子：如果“只修读取”的那次候选只换来一句“整体没有变好”，它很可能被扔掉，而它恰恰是正确修法的一半。更有用的反馈会说清：哪些案例变了，变化经过了哪个分支，违反了哪项约束，修复在哪些条件下仍然成立。这样下一轮才能提出不同的假设，而不是反复生成差不多的候选。

由 Agent 自己迭代时，这一点更要紧：它能改的地方多，搜索空间就大，从失败里学到的约束必须更明确。一段没验证过的长篇原因分析，代替不了可重放的输入、具体的修改和对应的后果。

## 记录要能被追问

要让这些实验成为日常能力，运行记录得为后面的问题服务。只存最终答案和一段解释，通常回答不了“如果当时读了另一处材料，结果会怎样”。我们需要知道实际调用了什么、返回了什么、哪些值被转换过，以及哪个规则版本用了它们。要回放开头的四格，至少得留下读出来的 100、用的是哪个版本的系数，以及两者相乘的那一步。

细节不必都永久保存，可以按预期的诊断操作来设计记录：要比较读取策略，就留下请求、材料身份和原始回执；要比较阈值，就留下进阈值之前的数值；要追踪对象拼接，就留下来源、对象和区域关系。记录多细，决定了能做哪些实验。

解释文本也有用，但要和这些可检查的对象连起来。模型说“我依据衣身孔洞作出判断”，可以帮我们提出假设；运行路径显示实际用了哪个事实节点，才能核对这句话。前者是系统的叙述，后者是重新检验叙述的入口。

有了这些，调试就成了一个清楚的循环：现象引出假设，假设要求特定的比较，比较排除一部分解释，剩下的解释指导局部改动。每一步都留下别人能复核的材料，团队换人、模型换版本，甚至原来的解释被推翻，它们依然有用。

## 回到开头

那个输出 80 的旧系统，按最终答案算是对的，里面却藏着两个错误；只修读取，方向明明是对的，按最终答案算反而是退步。只看结果，我们会留下错的、扔掉对的。四格回放把“改了这里，会发生什么”变成了可以逐格核对的问题。

理解一个系统，不需要掌握它的全部细节。在当前目标下分辨出几个重要机制，预测某个修改的后果，再用实验检查预测，就已经是可以积累的理解。这一篇能走到的终点，就是一项在明确条件下得到支持的改进：改了什么，为什么预期它有效，实验里发生了什么，适用范围在哪里，还有哪些问题没解决。到这一步，一次修复才有了值得保留的内容。

把这一篇压缩成可以带回项目的检查，大致是四个问题：

1. **对的案例，是不是碰巧对的？** 把中间结果单独核对一遍，看有没有两个错误在相互抵消。
2. **每个假设预测了什么？** 写下几个竞争的解释，以及各自预期的干预结果；做不出不同预测的假设，先别急着照它改。
3. **四格跑过了吗？** 两个部件都有新旧版本时，在同一批材料上把四个组合都跑一遍，看一项改动的效果是否取决于另一项。
4. **修复的账算全了吗？** 修好的、改坏的、仍然失败的都要看，还要看留出来的新材料上表现如何。

一次修复站住了，下一个问题随之而来：存下来，不等于将来用得好。下次遇到相似的问题，系统能不能认出这种相似？旧修法在新环境里会不会造成伤害？经验越攒越多，找到它们、维护它们，会不会本身成了新的成本？这些问题把我们带到最后一篇：怎样让一次成功，变成后续任务可以调用的能力。
