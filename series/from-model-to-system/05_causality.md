# 第五期 因果与实验 怎样找到有效的改变

[返回系列目录](README.md)

一个系统答错了，工程师通常能很快提出几种解释：图片没读清，检索没找到正确材料，规则覆盖得太宽，或者模型没有注意到某个例外。真正困难的工作发生在这些解释之后。它们都可能符合眼前的现象，我们却只能选择其中一部分去修改。下一次运行变好了，也未必能告诉我们上一次究竟错在哪里。

这件事在能够自行改写提示词、规则和程序的 Agent 中尤其明显。系统可以产生大量候选，却不一定知道哪一个改动值得保留。一次失败后写出一段流畅的分析，再生成一份新方案，是很容易观察到的行为；分析是否准确、方案为什么有效，需要另一套证据。

前一篇讨论结论怎样获得根据。这一篇继续追问：当我们准备改变系统时，什么样的根据足以支持这个改变？问题从“当前答案可信吗”，推进到了“如果动这里，后面会发生什么”。

## 正确结果里的两个错误

先看一个人为构造的小例子。任务是从材料中读取金额，再乘以业务规定的系数。材料上的金额为 80，正确系数为 1，因而目标结果是 80。旧系统把金额错读成 100，又错用了系数 0.8，最后仍然输出 80。

如果只检查最终答案，这个案例会被记为正确。现在我们分别修正读取和系数，得到四种组合。

| 读取结果 | 旧系数 0.8 | 修正系数 1 |
| --- | ---: | ---: |
| 旧读取 100 | 80 碰巧正确 | 100 错误 |
| 修正读取 80 | 64 错误 | 80 正确 |

单独修正读取，最终结果从正确变成错误。单独修正系数，也会得到错误。只有同时修正，两部分才共同恢复到正确机制。这个例子里的数字只用于推导，并非某次模型实验的统计结果，但它已经足以揭示一种真实的结构性可能：两个错误可以相互抵消，一个部件的改善也可能暴露另一个部件的问题。

因此，“这个案例原来做对了”不能直接证明原来的每个步骤都应保留；“这个改动让分数下降了”也不能单独证明改动中的每项判断都错了。最终指标当然重要，它衡量系统交付了什么。可当我们想决定下一步改哪里时，还需要了解结果怎样产生。

在复杂应用中，相互抵消往往没有乘法例子这么醒目。一项证据被错读成弱证据，恰好遇到过宽规则；一个检索器漏掉关键段落，生成器又凭已有知识猜对答案；某个判断路径有漏洞，另一条冗余路径却给出了正确输出。系统看起来稳定，内部问题却可能在输入稍有变化时一起暴露。

这也是为什么归因不能以“找一个能讲通的原因”为终点。解释需要告诉我们：如果它是真的，哪些可控改变应该带来哪些结果。只有这样，解释才能进入实验，而实验结果才能帮助我们选择行动。

## 我们究竟在解释哪一种因果

“为什么”在工程讨论中经常混合着几种不同问题。某个字段与错误经常一起出现，是一种统计关联；一条规则需要哪些前提，是一种逻辑依赖；修改某个模块以后输出发生变化，是软件系统中的干预效果；消费者实际如何使用商品、某个事件是否造成损坏，则属于现实世界的因果问题。

这些问题可以互相提供线索，却不能直接替代。比如，较长的请求更容易失败，可能因为长度增加了处理负担，也可能因为复杂请求同时更长、更难。仅从日志中选出长请求，会同时选入其他相关特征。把同一请求的某部分改变，再观察系统如何响应，才是在研究一个更明确的干预。

Pearl 对因果推断的一个核心区分，是从观测分布中的关联，转向改变条件之后会发生什么。这样的推断需要说明关于生成机制的假设；干预和反事实的答案并不能只由相关性自动给出。这一框架也提醒我们，把“影响”“原因”写进报告之前，先明确问题所指的变量和机制。[Pearl，2010](https://ftp.cs.ucla.edu/pub/stat_ser/r354-reprint-corrected.pdf)

软件系统提供了一个很有利的条件：部分机制由我们编写，部分状态可以保存，部分输入可以精确替换。如果规则引擎的输出完全由记录中的事实与规则版本决定，那么冻结其他条件，只改变一个事实，就可以明确计算这个替换对输出的影响。此时得到的是这个程序在指定条件下的响应。

假设程序将“衣身存在破洞”作为一个输入。把这一项由真改为假，结论随之改变，可以说明该项事实参与了当前程序的判断。它并没有说明现实中的破洞由谁造成，也没有说明这项事实最初读得是否正确。前一个问题需要现实证据，后一个问题需要核对观察过程。

概念瓶颈模型的研究明确使用了类似区分：修改模型预测的中间概念，可以观察最终预测如何变化；这与在现实中改变相应概念、观察现实结果是否变化，是不同的干预对象。[Koh 等，2020，第 2 节](https://proceedings.mlr.press/v119/koh20a/koh20a.pdf)

这种区分有直接的设计价值。系统内部的可控替换适合定位计算链路中的依赖和敏感性；现实因果问题则需要相应的观察、实验或识别条件。把两者说清楚以后，程序反事实的价值反而更具体了：它让我们能够精确询问，一项假设如果改变，这个系统会如何重新计算。

## 从失败现象写出竞争假设

看到一个错案时，最容易得到的解释通常是最熟悉的解释。一直在改提示词的人会先怀疑提示词，维护规则的人会先怀疑规则，负责数据的人会先怀疑样本质量。要让诊断超出各自的习惯，需要把解释写成具有不同预测的假设。

仍以多模态判断为例。系统认为衣身破损，检查原图后却发现孔洞位于吊牌。至少存在三种可能：观察模型认错了对象；观察结果区分了对象，但中间接口没有保存归属；归属被保留了，规则执行时却把不同对象的属性拼在一起。它们都能产生同一个最终错误，修法却不同。

如果怀疑观察错误，可以把经过核对的对象身份放入原接口，保持规则不变，查看结论是否恢复。如果怀疑接口丢失关系，可以检查原始回执中是否已有对象信息，以及后续状态是否还能表达它。如果怀疑执行规则忽略绑定，可以提供一份明确区分对象的输入，直接检查规则是否仍然跨对象组合。

这里的关键是让假设承担预测责任。“模型没理解”太宽，几乎任何结果都能被它解释；“对象身份在提取回执中正确，但在合并时被丢掉”则预测了一个具体的差异位置。我们可以比较合并前后状态，也可以构造只交换对象归属、保留其他属性的材料。假设越具体，需要检查的范围越清楚。

但具体并不等于假设之间必须互斥。一个系统可能既存在读取错误，也存在规则过宽。纠正读取之后，规则问题仍然存在；单独收紧规则，又可能掩盖错误读取。开头的四格例子已经说明，诊断需要容纳共同作用，不能强迫每个失败只归入一个类别。

实验还应当区分“这个信息如果正确会怎样”与“我们能否稳定获得正确信息”。人工替换一个错误字段，可以证明这个字段值得关注，也可以估计理想修正的潜在收益；它没有证明换一段提示词就能实现同样的改善。前者是诊断实验，后者需要真实的读取过程来检验。

同样，直接把最终答案改成参考答案，总能修好当前案例，却没有解释任何机制。一个有用的候选应当落实到可以重复执行的变化：改了哪个问题，增加了哪个观察，补上了哪种关系，缩小了哪条规则的范围。只有这些变化，才可能在新材料上接受检查。

## 把改动变成能够比较的实验

为了比较改动，需要先明确实验单位。对一个两阶段系统，可以把每份固定材料视为一个单位，将观察版本记为 O0、O1，规则版本记为 R0、R1。每份材料都运行四个组合，并保存对应的中间状态和输出。

四格的价值来自同一份材料上的配对比较。O0R0 与 O1R0 比较观察变化在旧规则下的效果，O0R1 与 O1R1 比较同一变化在新规则下的效果。在确定性回放中，若两次效果不同，就说明观察改动的作用取决于规则环境。对于随机模型，则需要通过重复运行或足够多案例估计这种差异，并检查采样波动；一次四格运行不足以确认稳定的交互。对规则的比较也完全类似。

把某个已经约定的质量指标记为 q，四个值分别记为 q00、q10、q01、q11，可以用下面的量描述加法尺度上的交互：

```math
I = (q_{11}-q_{01})-(q_{10}-q_{00})
```

它比较“新规则下改变观察的收益”与“旧规则下改变观察的收益”。开头例子如果按最终答案是否正确记为 1 或 0，四个值依次为 1、0、0、1，交互量为 2。这个数表示在所选二元质量尺度上的强烈交互，不是两项改动创造了百分之二百的业务收益。换用绝对误差等指标，数值和解释尺度也会变化。

因此，面对联合改善，常常没有一个脱离评价方式和比较顺序的唯一“贡献百分比”。可以规定分配办法，也可以分别报告各条件下的边际效果，但这些选择应当明示。先回答“改变在什么条件下有效”，通常比急着把收益分给不同模块更有助于下一步设计。

冻结条件也需要足够具体。仅固定案例编号还不够：原始材料、规则版本、工具返回、相关阈值与上下文，都可能改变执行结果。对于具有随机性的模型，保存某一次原始回执适合分析该次轨迹；要判断新提示词的稳定效果，则需要多次运行或足够多的新案例，报告波动，而不能把单条轨迹的差异当成稳定收益。

混合版本之间还必须有可解释的接口。如果新观察将“破损”拆成三个不同概念，旧规则却只接受一个布尔量，那么 O1R0 并不是天然定义好的实验。我们必须说明怎样转换，以及转换是否丢失信息。否则，测到的差异可能主要来自兼容层，而不是原本想比较的观察方法。

对检索问答系统也可以做同样分析。保存旧检索器与新检索器分别返回的文档，再让旧提示词和新提示词各自消费两份检索结果。这样可以区分：新证据本身是否有帮助，生成器能否利用已有证据，以及两个变化是否需要共同出现。若所有模块一起更换，只留下最终分数，这些问题就会失去直接的比较依据。

对于会根据中间结果继续行动的 Agent，还需要区分局部回放和完整运行。换一个提示词，可能让它选择另一项工具；工具返回不同材料，后续轨迹也随之变化。如果强行冻结全部后续输入，我们隔离了某个节点的处理差异，同时也切断了新策略原本可能获得的收益。这个实验适合解释局部机制，不能直接代替完整策略的验收。

相应地，可以先用局部替换确认一条错误路径，再让候选从相同起点完整运行，检查它是否真的以预期方式获得信息并完成任务。两种实验有不同的固定条件：前者控制更多变量，后者保留行动之间的反馈。报告中说明各自在回答什么，便能避免把“这一节点使用相同证据时更好”误写成“整个 Agent 已经稳定更好”。

如果完整运行的表现波动较大，还要检查变化是否集中在某种分支。平均分接近，可能掩盖一个路径获得改善、另一个路径受到损害。把结果重新对应到经过的操作与适用条件，才能决定下一轮应该缩小修复范围，还是继续改变策略。

## 一个结论可能有不止一条支撑

有时，翻转一个事实后输出没有变化，容易被解释成这个事实不重要。但不变也可能来自另一条仍然成立的支撑路径。

考虑一个简化规则：只要“存在结构损伤”或“承诺不符”其中一项成立，就可以推出应当进入某种处理。这里把输出限定为“当前前提是否足以推出这一处理”，把撤销定义为不再将某项事实作为可用前提，并不自动将它判为假。当前两项都成立。单独撤销结构损伤，承诺不符仍支持结论；单独撤销承诺不符，结构损伤仍然支持结论。联合撤销后，当前给定的前提不再足以推出这一处理，但这并未证明相反的处理才正确。

这里单个事实的零边际效果，并不表示它不能独立支撑结论。我们需要研究支撑集合，以及哪些集合被同时移除后，结论便不再能由当前前提推出。若一个撤销集合能造成这种变化，而它的任何真子集都不能，就可以称它为一个最小撤销集合。这是针对当前规则和当前输入的逻辑性质。

“最小”也有多种含义。集合包含关系上的最小，未必是元素数量最少，更未必是实际操作代价最低。有一项观察很便宜，另一项需要重新联系外部来源；即使两种撤销方式都只涉及一个字段，真实成本也可能不同。逻辑分析给出候选，工程决策还要加入可实现性和代价。

此外，任意翻转字段可能构造出不可能的状态。例如，一个对象被标记为既未出现，又有经过确认的局部细节；某个数值与由它计算得到的类别互相矛盾。这样的输入可以用来测试程序的防御能力，却不一定是合理的现实反事实。要研究实际可发生的修改，就应保持对象关系、派生约束和证据范围的一致性。

这让“生成反例”成为一项需要领域结构的工作。每次构造都需要说明改变了什么，以及哪些条件应当保持。检查关键因素时，可以固定对象身份，改变衣身是否有孔的证据，观察规则是否作出相应响应；检查无关因素时，则可以保持衣身证据不变，改变吊牌状态，观察结论是否异常变化。只调整图片排列顺序、保持事实含义不变，也属于后一种不变性检查。两种检查分别检验系统是否响应了应当关心的变化，以及是否受到了不应关心的变化影响。

这些检查各自回答有限而明确的问题。符合预期的结果增加了对某个机制解释的支持，不代表所有潜在输入都已经被覆盖。它们的力量来自针对性：每一次变化都有理由，每一次输出变化都可以对应回正在检验的假设。

## 从解释走向可采用的修复

一个解释能说明已有错误，还需要面对未参与构造它的材料。最容易过度乐观的时刻，是候选已经在几个熟悉案例上全部奏效的时候。此时我们对失败机制知道得更多，但也已经反复看过这些案例，规则很可能逐渐贴合了它们的细节。

因此，修复的验收应该包含两种不同材料。一类是针对机制构造的边界案例，用来检查规则是否真的遵守了声称的区别；另一类是保留的新材料，用来检查这种区别在更广的分布上是否有用。前者帮助解释，后者帮助估计可迁移的效果，两者提供的证据不能互相顶替。

例如，收紧一条“有孔即破损”的规则，可能修复吊牌误判，却漏掉某些真实衣身孔洞。检查影响范围时，需要同时查看被修复的错误、原先正确而现在改变的案例，以及仍然失败的案例。只展示成功翻转的部分，会丢掉决定这项修法能否采用的信息。

修复还可能改变资源使用。增加一次定向读取，可以提高一类边界情况的判断质量；如果每个案例都触发同样的读取，成本可能很高。原因解释若能准确界定适用范围，就可以让额外操作只发生在需要它的地方。此时归因不只帮助提升正确率，也帮助决定计算和观察预算花在哪里。

一次候选被拒绝，反馈也需要足够具体。如果反馈只说“整体没有变好”，下一轮很难知道哪里应当保留。更有用的材料包括：哪些案例改变了，变化经过哪个分支，哪项约束被违反，哪些条件下的修复仍然成立。这样的反馈可以支持下一轮提出不同假设，而不是重复产生近似候选。

当系统由 Agent 自行迭代时，记录这些信息尤其重要。Agent 能够修改很多地方，意味着搜索空间更大，也意味着从一次失败中学习到的约束必须更明确。一个未经验证的长篇原因分析，不能替代可重放的输入、具体的修改与对应后果。

## 为归因保留可以追问的记录

要让这些实验成为日常能力，运行记录就需要服务于后续问题。仅保存最终答案和一段解释，通常不足以重新回答“如果当时读取另一处材料，结果会怎样”。我们需要知道实际调用了什么、回来了什么、哪些值经过了转换，以及哪个规则版本使用了它们。

这并不要求把所有细节永久保留。可以先围绕预期的诊断操作设计记录：如果需要比较读取策略，就保留请求、材料身份与原始回执；如果需要比较阈值，就保留阈值之前的数值；如果需要追踪对象拼接，就保留来源、对象和区域关系。记录粒度与可做的实验共同决定。

解释文本也有作用，但它应该与这些可检查对象连接。模型说“我依据衣身孔洞作出判断”，可以帮助提出假设；运行路径显示实际使用了哪个事实节点，才能进一步核对这个说法。前者是系统给出的叙述，后者提供了重新检验叙述的入口。

在此基础上，调试会形成一个更清楚的循环：现象引出假设，假设要求特定比较，比较排除一部分解释，剩下的解释指导局部改变。每一步都能留下别人可以复核的材料。团队成员更换，模型版本变化，甚至原先的解释被推翻时，这些材料仍然可能有用。

## 一次有根据的改变

理解一个系统，并不意味着已经掌握了它的全部细节。在当前目标下，能够分辨若干重要机制，预测某种修改的后果，并用实验检查预测，已经是一种可以积累的理解。

这种理解也会改变我们面对失败的姿态。一个最终错误，不再只是一条待补充的提示词；一个最终正确，也不再自动成为所有内部选择的背书。我们开始关心，哪些条件共同支持了结果，哪些变化会使它失效，以及怎样以最小必要的代价获得新的区分性证据。

本篇能够抵达的终点，是一项在明确条件下得到支持的改进：改了什么，为什么预期它有效，实验中发生了什么，适用范围在哪里，还有哪些问题尚未解决。到了这里，一次修复才有了可保留的内容。

但保存下来并不等于未来能够用好。下一次遇到相似问题，系统能否识别出这种相似？旧修法会不会在新环境中产生伤害？经验越来越多以后，寻找和维护它们是否反而成为新的成本？这些问题把我们带到最后一篇：学习怎样使一次成功成为后续任务可以调用的能力。
