# 第二期 语言 怎样让意图成为明确的表达

[返回系列目录](README.md)

## 一句人人都懂的话

“下周安排一次半小时讨论，主要参与人都能来，尽量照顾不同时区，先给我方案。”

这是一条再普通不过的工作请求。熟悉团队的同事大概知道该怎么做，语言模型也能很快回一段流畅的话。可系统一旦真要动手，问题就一个接一个冒出来：下周从哪天算起？谁算主要参与人？“都空闲”和“都方便”是一回事吗？照顾时区，拿什么比？“先给方案”允许查日历，那允许先占会议室吗？

原句没有说错什么。人和人协作，很多含义靠共享背景撑着：我们知道团队的习惯、每个人的角色，也知道这类请求通常做到哪一步为止。自然语言把这些背景留在句子外面，所以才简洁。麻烦在于，进了自动系统，这些背景从哪里来，又在哪一步被定下来？

上一篇问的是表征：任务需要的对象、属性和关系有没有被保留。这一篇假定参与人、时段、时区、会议室这些对象都已经在了。接下来要问的是：怎样把它们组织成要求，又怎样判断一个结果满足了要求。这就是语言的问题。

## 一句话，四种成分

先把这条请求拆开。“半小时”规定会议长度，“主要参与人”指向一组具体的人，这是要落实的事实；“都能来”规定候选时段必须满足的条件；“尽量照顾时区”说的是合格方案之间还要比一比；“先给我方案”划定这一次能做到哪一步。

这几样东西不能混着处理。如果全写成一组必须满足的布尔条件，偏好就被当成了硬要求：让所有人都在本地白天开会，可能根本找不到共同时间。如果全折算成一个加权总分，系统又可能用一堆小方便，抵掉一位关键参与人来不了。两种做法都改掉了请求原来的结构。

所以先立几条约定：必要参与人的日历必须空闲，这是硬约束；在可行时段里，尽量减少落在本地休息时间的人数，这是偏好；给出三个候选让人挑，这是这一次的产出；创建日历事件，不在这一次的动作范围内。这些约定可以用自然语言写，也可以写成一张小表：

| 内容 | 在当前任务中的作用 | 需要进一步确定的地方 |
| --- | --- | --- |
| 主要参与人 | 决定哪些日历约束必须满足 | 对应哪些具体身份 |
| 半小时 | 规定持续时间 | 是否另加会前缓冲 |
| 都能来 | 排除不合格时段 | 空闲是否已足够 |
| 照顾时区 | 比较合格候选 | 采用什么偏好规则 |
| 先给方案 | 限定当前动作 | 候选数量与展示内容 |

这张表已经是一种语言设计：它规定了哪些内容可以出现、各自扮演什么角色、怎样影响系统的行为。价值不在整齐，而在于不同性质的要求不再搅在一起。

最后一列同样要紧。有些空可以从可靠的背景里补上，有些要回头问人，有些可以用事先约好的默认值。关键是每个解释都查得到来路。比如团队规定了“主要参与人”以某份项目名单为准，系统读名单就行；没有这条规定，模型凭姓名出现的次数去猜谁重要，就是悄悄加了一个没人说过的假设。

接口设计也跟着变。查日历要确定身份，生成候选要确定约束，真正执行要确定权限，它们可能来自不同环节。好的表达允许未定项先挂着，并让下一步知道还缺什么。

## 括号放在哪里

再看一句更短的话：“满足 A 或 B 且 C”。它可以读成“满足 A，或者同时满足 B 和 C”，也可以读成“先满足 A 或 B，再额外满足 C”：

```math
A\lor(B\land C)
```

与

```math
(A\lor B)\land C
```

A 为真、C 为假时，前一个成立，后一个不成立。括号没有添加任何事实，它只规定事实怎么组合。每个词都看得懂，组合方式一变，整句要求就变了。在具体语境里，人往往一眼看出作者的意思；但要稳定执行的系统，必须把组合范围定死。

这里有三层东西。语法管结构：哪些符号能组成合法的表达，各部分怎样嵌套。语义管解释：一个条件满足没有，一个查询返回什么，一个动作带来什么状态变化。语境帮我们确定当前说的是谁、以什么时间为基准、默认了什么。“下周”人人会用，但只有结合今天的日期和一周从哪天算起，它才落成一段具体的区间。

三层都会出错，错法各不相同。表达式语法合法，却指错了对象；日期计算严格遵守程序规则，却把参与人所在地的日期当成了组织者所在地的日期；模型生成的 SQL 能跑，回答的却是一个范围略有不同的问题。

把自然语言翻成形式表达，其实同时做了两件事：选定一种解释，再把这种解释写下来。两件事要分开检查。语法检查能抓出漏掉的括号，替代不了对“主要参与人”名单的确认；执行器会忠实地遵守给定的约束，却判断不了这些约束是不是提请求的人心里想的那些。第一篇里的黎曼猜想核验，单独检查形式化命题是不是那个猜想，查的就是第一件事。

> 一段表达能被解析、能被执行，不等于它说的还是原来那件事。

第一件事要靠例子来查。抽象地谈“照顾时区”，大家都会点头；把两个候选摆在面前，一个让两个人稍晚参加，另一个让一个人凌晨参加，分歧才会出现。例子把含糊的偏好变成看得见的后果，解释才有机会被修正。

## 小零件，大要求

如果每一种会议要求都要写一段全新的程序，系统很快就没法维护。我们希望“这段时间有空”“时长三十分钟”“在工作时间内”这样的小概念能反复使用，再用清楚的规则拼成复杂的要求。

设想一个很小的表达体系。Free(p,t) 表示参与人 p 在时段 t 内空闲，Duration(t) 表示时段长度，Required 是必要参与人的集合。一个合格的时段可以写成：

```math
\mathrm{Valid}(t)=
\bigl(\mathrm{Duration}(t)=30\text{ minutes}\bigr)
\land
\bigl(\forall p\in\mathrm{Required},\ \mathrm{Free}(p,t)\bigr)
```

知道时长，知道每个必要参与人有没有空，就能算出这个时段在当前约定下合不合格。以后要加“会议室必须可用”，再并上一个条件就行；必要参与人换了，时长的定义一个字也不用动。

这就是组合语义在工程上的用处：复杂表达的含义，由部件的含义和组合规则决定。改一个部件，可以直接问哪些上层表达依赖它，不必把所有句子重新解释一遍。

变量和作用域最容易在这里出事。“每个必要参与人都有空闲时段”和“有一个时段，所有必要参与人都空闲”是两个条件。前者允许每个人的空闲时间互不重叠，只有后者才保证真的能开会。

```math
\forall p\ \exists t\ \mathrm{Free}(p,t)
\qquad\text{与}\qquad
\exists t\ \forall p\ \mathrm{Free}(p,t)
```

两个式子用的符号一模一样，只是量词换了顺序，业务上却是“未必能开会”和“能开会”的差别。模型生成规则或查询时，关键词全都出现了，也不保证组合是对的。要检查的是变量绑在谁身上、量词管到哪里、条件之间是什么关系。上一篇的对象归属问题，在这里有了一套能明确写下来的表达方式。

命名让一组条件变成一个可以反复调用的概念。把“时长正确、必要参与人空闲、会议室可用”叫作“可行候选”，后面就可以集中比较可行候选之间的偏好。但名字不会让复杂性消失。它好不好用，取决于定义稳不稳、调用方式清不清楚，以及定义改了之后，能不能知道哪些地方受影响。

## 九点不只是一个数

时间最容易暴露语言的问题。一个不带时区的“上午九点”、一个确定的全球时间点、一段三十分钟的时长，都可以存成数字或字符串，能参与的运算却各不相同。

时长可以相加；时间点加上时长，得到另一个时间点；两个不同地方的本地时间，没有日期和时区，就不能拿来判断是否重叠。如果只存数值，每次运算都得猜这个数是什么意思。类型把这些差别写进了表达规则。

参与人也一样。显示名称不是账户标识：两个同名的人显示名称相同，却不是同一个参与人。会议候选也不是已经建好的日历事件：字段可能很像，支持的操作和承诺的状态却不同。

类型检查能提前挡掉没有定义的组合：不许把时长当成会议开始时刻，不许把候选的临时编号当成已建事件的标识。错误不必等到执行时才暴露，调用方也知道一个操作要什么输入。

类型管的是结构约定，不管事实。一个时间值类型完全合法，日期却可能是错的；一个对象被标成“必要参与人”，实际可能是模型选错了人。值和现实对不对得上，仍要靠各自的证据。

未知状态也需要约定。日历读取失败，不等于这个人有空；某位参与人的时间还没拿到，也不能顺手记成“不参加”。表达体系要说清楚：缺失值怎样影响条件，哪些操作可以带着未知继续，哪些必须等信息补齐。这和上一篇里“没看到”不等于“没有”是同一件事。

类型不必一次设计齐全。从真实出现过、并且会导致不同后续动作的区别出发，一种一种地加。每加一种，都要说得出它挡住了哪类错误，或者让哪个原本含糊的操作变得明确。

## 都能写，为什么还要挑

如果一门通用编程语言就能把会议助手写出来，为什么还要讨论规则表达式、查询语言或者小型 DSL？反过来，一旦设计了专门的规则语言，是不是所有逻辑都该塞进去？

两个问题都不能只看“能不能表达”。通用语言实现空间大，但一些重要的领域结构，要靠额外的约定才认得出来。专门的表达形式能让某些关系直接摆在明面上，却可能缺少任务需要的能力，还要额外维护它自己的工具。

Felleisen 研究编程语言的表达能力时指出，比较可计算函数的集合，区分不开许多通用语言。他转而研究：某种构造能否以保持结构的方式消去，翻译时是否需要重组更大范围的程序。[Felleisen，1991](https://www.cs.tufts.edu/~nr/cs257/archive/matthias-felleisen/expressive-as-published.pdf) 这里借的是他的视角，不是他的形式结论：表达能力不只看能算出什么，还要看结构怎样被组织、被保存。

放回会议系统。规则如果是一组明确的条件和偏好，程序可以逐条找出哪个条件没满足、比较候选、定位冲突。同样的逻辑包进任意函数里，这些分析也做得到，但要额外的约定，或者真的跑起来、另做分析。计算能力相同的语言之间，要比的是谁更好地保住了程序结构，分析和维护各要付出多少；受限的领域语言，还要单独查它覆不覆盖任务所需。

专门语言也有边界。只支持简单布尔条件，就表达不了时间区间之间的关系；没有集合操作，使用者只能把参与人一个个手动展开；没有清楚的状态语义，“提出方案”和“建立事件”就会混成一件事。为每个特殊情况加一个运算符，语言又会越来越难懂。

所以选表达形式，要从需要的操作倒推：要执行，就得有执行语义；要找冲突，重要约束就得能被识别；要比较规则版本，变化就得落在可追查的结构上；要开放的理解，原始的语言材料也得留着。自然语言、通用代码和领域表达可以各管一段。

实际选择时，先从已有的查询、配置、逻辑或编程语言出发，复用现成的工具和知识；要设计新形式，就得说清楚现成的形式在哪项关键操作上碰到了具体困难。语言的收益，要和生成、理解、执行、维护的成本放在一起算。

也可以只把一部分写严格。会议必须避开的日历冲突，可以有确定的语义；会议主题适不适合某位参与人，可以留作带依据的建议。两部分的接缝要清楚：建议怎样影响排序，能不能推翻硬约束，哪些内容还在等人拿主意。形式化做到哪里，由实际需要决定；没说清的内容，也有自己的位置。

## 并列第一算几个

换一个领域。“找出每个部门收入最高的人。”这句话看着简单，至少有几处没定：部门按现在的归属算，还是按收入发生时的归属算？收入是工资、奖金，还是一段时间的总额？并列最高要不要都返回？收入缺失的人参不参与比较？

假定前两个问题已经确认：按当前部门，只看一列明确的月收入。还剩并列。为了只看并列这一件事，先假设参与排名的收入都不为空，按部门分区，窗口内只按收入降序排列。一个部门里如果有两人收入相同且最高，逐行编号后取第一行，和排名后返回所有第一名，结果就不一样。PostgreSQL 对 row_number 和 rank 的定义正好体现了这个差别：前者给每行分配行号，后者让排序上相同的行得到同一名次。[窗口函数文档](https://www.postgresql.org/docs/current/functions-window.html)

两条查询都能合法执行；在没有并列的数据上，结果还一模一样。所以拿一份普通数据测一遍，分不出它们表达的是不同的要求。必须专门造一个有并列的例子，才能检查实现保住了已经确认的含义。

再放开“收入不为空”的假设，又会碰到缺失值怎么解释。SQL 里，普通比较运算遇到 NULL，通常得到未知，而不是真或假；判断是否为空，要用专门的谓词。[比较运算文档](https://www.postgresql.org/docs/current/functions-comparison.html) 如果模型把“收入未知的人”换成了“收入为零的人”，代码照样能跑，数据的含义却变了。

所以自然语言转 SQL，至少要过三道检查：先定下范围、并列、缺失值这些解释；再查生成的表达是否对应这些解释；最后查数据和执行结果。语法正确只是其中一小部分。

反例在这里特别好用：一个专测并列，一个专测空值，一个专测跨部门的范围。每个例子目的清楚，也让提请求的人看到某个选择会带来什么后果，形式表达和人的意图因此始终能放在一起讨论。

会议助手也可以这样测。三个情形就够：所有人都有空，但没有共同的空闲时间；所有候选都会碰上某人的休息时间；某个人的日历还没读到。它们分别检查量词范围、偏好取舍和未知状态的处理，不用模拟整个生产环境，就能先把语言层面的分歧逼出来。

## 定义也会变

系统上线以后，语言不会停下来。团队可能重新划定谁是必要参与人，新的工作习惯改变了对休息时间的判断，也可能加上一条“允许一位非必要参与人缺席”。如果这些变化只散落在各处的提示词里，同一个名称就会在不同模块里慢慢长出不同的意思。

要守住共同含义，关键概念就得找得到、有版本。一条规则应当知道自己用的是哪一版定义，一次结果应当能回到当时的解释。这样，“可行候选”的含义变了以后，我们分得清两件事：新任务按新规则跑，旧结果在旧规则下对不对。

例子也要跟着定义更新。过去接受的安排现在要排除，测试的改动应当对应一项明确的要求变化，而不是为了让新程序通过就去改答案。否则测试就不再检验语言和意图是否一致。

自然语言说明在这里依然重要。形式表达擅长把选定的解释钉住，原始说明和讨论记录则保存了为什么这样选、还有哪些问题没定。两者都在，维护者才不会对着一条精确的规则，却不知道它为什么在那里。

组合时还会出现冲突。两条规则各自合理，合起来却可能一个可行结果都没有：一条要求所有人都在本地上午参加，而参与人分布在相隔很远的时区。语言能把冲突说清楚，解决冲突却要回头重新商量约束、偏好或任务范围。加多少计算预算，都不会自己决定谁的方便该让一让。

所以语言也是协作的设施：分歧落在具体的表达上，约定可以反复使用，修改能追到受影响的地方。人和系统不用每次重猜所有背景，但修改约定的入口要一直留着。

## 说清楚了，还没找到

回到会议请求。到这里，参与人、时间区间、时长、硬约束、偏好和本次动作都已经明确。系统说得出什么算可行、方案之间怎么比、给出方案之后还要谁来拍板。

但这些都还没有找到一个合格的时段。参与人的日历可能排得很满，候选可能非常多；如果任务扩大成一整天的研讨会，还会冒出讲者冲突、房间安排、场次顺序这些组合问题。

表达和求解能连起来，却不能互相替代。表达决定什么算对，求解负责找到满足要求的东西。求解器可以忠实地找出某组条件下的最优解；条件理解错了，最优也救不回来。反过来，要求写得再清楚，也不会自动送来一个高效的算法。

## 回到开头

“下周安排一次半小时讨论，主要参与人都能来，尽量照顾不同时区，先给我方案。”句子没有变，变的是系统读它的方式。它被拆成了事实、硬约束、偏好和动作范围；“主要参与人”指向一份名单，“下周”落到一段日期；“都能来”是“存在一个时段，所有人都空闲”，而不是反过来；读不到的日历记为未知，不记为有空；“先给方案”到候选为止，不碰日历事件。

语言的工程价值，就在于让这些问题可以分开提出：哪项要求被漏掉了，哪个量词的范围变了，哪个状态不允许执行哪个动作，哪个概念还需要讨论。应用因此有了一份能检查、能协商、能修改的共同形式。

把这一篇压缩成可以带回项目的检查，大致是四个问题：

1. **每一部分是什么？** 请求里的每一部分，是事实、硬约束、偏好，还是这一次的动作范围；由谁来定，没定的部分挂在哪里。
2. **组合写对了吗？** 关键词都出现不算数，要看变量绑在谁身上、量词和括号管到哪里；有没有一个例子能把两种读法分开。
3. **类型挡住了什么？** 时长和时间点、显示名称和账户、候选和已建事件是否被区别对待；未知会不会被悄悄当成“有空”或“为零”。
4. **普通数据测不出的情形，有没有专门的例子？** 并列、空值、没有共同空闲、日历未读到，是否各有一个小例子；定义改了，例子是否跟着改，并且每处改动都对应一项明确的要求变化。

下次出错时，先分清问题落在哪一层。概念和组合范围还没定，就回去澄清、调整表达；算出了满足规格的结果，实际用起来还是有问题，就回头查规格和任务之间的联系。如果语义已经确定，候选却找得又慢又差，那就不再是语言的问题，而是下一个问题：在有限的时间和资源下，怎样找到一个足够好的答案？计算篇将从同一份会议要求出发，看搜索、约束与资源分配怎样改变解决问题的过程。
