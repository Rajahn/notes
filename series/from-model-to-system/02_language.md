# 第二期 语言 怎样让意图成为明确的表达

[返回系列目录](README.md)

## 一句话中的事实约束与行动

“下周安排一次半小时讨论，主要参与人都能来，尽量照顾不同时区，先给我方案。”

这是一条普通的工作请求。一个熟悉团队的人大概知道它想做什么，一个语言模型也很容易给出流畅的回应。然而，系统真正开始行动时，会遇到一连串尚未确定的事情：下周从哪一天开始，哪些人算主要参与人，所有人都空闲与所有人都方便是否相同，照顾时区怎样比较，先给方案允许查询日历，却是否允许占用会议室？

这些问题并不意味着原句表达失败。人与人协作时，许多含义依靠共享背景维持。我们知道团队习惯、参与者身份，也知道一份请求通常允许做到哪一步。自然语言能够把大量背景留在句子之外，使交流保持简洁。问题在于，进入一个自动系统之后，这些背景究竟从哪里来，又在哪一步被确定下来。

上一篇讨论表征：系统是否保留了任务所需的对象、属性与关系。现在假定参与人、时段、时区、会议室等对象都已经存在，我们仍然需要一种方法，把它们组织成要求，并约定怎样判断一个结果满足要求。这便进入语言的问题。

语言让复杂意图可以由较小的部分构成，也让不同的人和程序能够围绕同一份表达开展工作。但一段表达能被解析、能被执行，尚不足以证明它忠实保留了原来的意图。理解语言的工程意义，需要同时看表达的结构、解释规则和使用情境。

先把会议请求里的几类内容分开。“讨论持续半小时”规定了会议长度；“主要参与人都能来”规定候选时段必须满足的条件；“尽量照顾时区”说明合格方案之间还需要比较；“先给我方案”规定当前执行的范围。

如果把这些内容全部写成一组待满足的布尔条件，偏好可能被误当成必须满足的要求。所有参与者都在本地白天参加，可能根本不存在共同时间。如果把所有要求都变成一个加权分数，系统又可能用很多小的便利，抵消一位关键参与者无法出席。两种做法都改变了请求原来的结构。

因此，我们可以先作出一组明确的约定：必要参与人的日历必须空闲，这是硬约束；在可行时段中，优先减少处于本地休息时间的人数，这是偏好；输出三个候选供人选择，这是当前任务的结果；创建日历事件尚未包含在本次动作中。这些约定可以写成自然语言，也可以写成一个小型结构。

| 内容 | 在当前任务中的作用 | 需要进一步确定的地方 |
| --- | --- | --- |
| 主要参与人 | 决定哪些日历约束必须满足 | 对应哪些具体身份 |
| 半小时 | 规定持续时间 | 是否另加会前缓冲 |
| 都能来 | 排除不合格时段 | 空闲是否已足够 |
| 照顾时区 | 比较合格候选 | 采用什么偏好规则 |
| 先给方案 | 限定当前动作 | 候选数量与展示内容 |

这张表已经体现了一种语言设计。它规定哪些内容可以出现，各自承担什么角色，以及它们如何影响系统行为。表的价值不在于格式整齐，而在于不同类型的要求不会再不加区别地混合。

其中有些信息可以从可靠背景中取得，有些需要进一步询问，有些允许采用事先约定的默认值。重要的是让解释可以被追查。例如，团队已经规定“主要参与人”由某个项目名单决定，系统便可以读取名单；如果没有这样的规定，模型仅凭姓名出现的次数推断重要性，就增加了一个未经说明的假设。

这个区别会直接影响接口设计。查询日历时需要确定的身份，生成候选时需要确定的约束，执行动作时需要确定的权限，可能来自不同环节。一种合适的表达应当允许未确定项暂时保留，并使下一步清楚地知道还缺少什么。

## 语法与含义之间

考虑“满足 A 或 B 且 C”这句话。它可能被读成满足 A，或者同时满足 B 和 C；也可能被读成先满足 A 或 B，再额外满足 C。在某个具体语境中，人可能轻易知道作者想表达哪一种，但一个需要稳定执行的系统必须固定组合范围。

```math
A\lor(B\land C)
```

与

```math
(A\lor B)\land C
```

在 A 为真、C 为假时，得到不同结果。括号没有添加新的事实，它规定了事实怎样组合。句子中的词都可以理解，组合方式仍然可能改变整个要求的含义。

语法处理表达的结构：哪些符号能够组成合法表达，各部分怎样嵌套。语义规定这些合法表达怎样被解释：一个条件是否满足，一个查询返回什么，一个动作产生什么状态变化。语境则帮助我们确定当前谈论的对象、时间基准和背景约定。例如，“下周”具有可理解的用法，但只有结合当前日期和周的划分规则，才能落实成一段具体区间。

这三个层次会共同影响应用。一个表达式可能在语法上合法，却使用了错误的对象；一个日期计算可能完全遵守程序规则，却把参与者所在地的日期当成了组织者所在地的日期；一个模型也可能生成合法 SQL，却回答了另一个范围稍有不同的问题。

把自然语言翻译成形式表达时，我们通常会同时完成两项工作：确定某种解释，以及把这个解释编码。两项工作需要不同的检查。语法检查能发现括号缺失或非法结构，不能代替对“主要参与人”名单的确认。执行器能够忠实地遵守给定约束，但无法仅凭约束本身判断它是否符合提出请求的人原来的想法。

这也解释了为什么形式化需要例子。抽象地讨论“照顾时区”，不同的人可能都表示同意；把两个候选放在面前，一个让两个人稍晚参加，另一个让一个人凌晨参加，分歧才会出现。例子将含糊的偏好转成可以比较的后果，使解释有机会被修订。

## 组合怎样使表达可以扩展

如果每一种会议要求都需要一段全新的程序，系统很难维护。我们希望“时段内空闲”“持续三十分钟”“位于工作时间”等简单概念可以反复使用，并通过清楚的组合方式形成复杂要求。

可以设想一个很小的表达体系。Free(p,t) 表示参与人 p 在时段 t 内空闲，Duration(t) 表示时段长度，Required 表示必要参与人的集合。一个合格时段可以表达为：

```math
\mathrm{Valid}(t)=
\bigl(\mathrm{Duration}(t)=30\text{ minutes}\bigr)
\land
\bigl(\forall p\in\mathrm{Required},\ \mathrm{Free}(p,t)\bigr)
```

这个表达式把两个要求组合起来。知道时长和每个必要参与者的空闲状态，就能够计算当前约定下的合格性。以后增加“会议室必须可用”，可以加入另一个条件；改变必要参与人集合，不需要重写时间长度的定义。

这就是组合语义在工程中的价值：复杂表达的含义，能够依据部件的含义和组合规则得到。它使局部修改、复用和检查具有较稳定的范围。当我们改变一个部件时，可以追问哪些上层表达依赖它，而不必把所有句子重新解释一遍。

变量和作用域在这里尤其重要。“所有必要参与人至少有一个空闲时段”，与“至少有一个时段让所有必要参与人都空闲”，是不同的条件。前者允许每个人的空闲时段互不重叠，后者才保证存在共同会议时间。量词排列对应了一个直接的业务差别。

```math
\forall p\ \exists t\ \mathrm{Free}(p,t)
\qquad\text{与}\qquad
\exists t\ \forall p\ \mathrm{Free}(p,t)
```

当语言模型生成规则或查询时，所有关键词都正确出现，并不保证这些组合关系正确。检查表达，需要检查变量绑定、量词范围和条件之间的关系。上一篇中的对象绑定问题，在这里获得了一套可以明确写下来的表达方式。

命名则帮助我们把一组条件当作一个可重复使用的概念。例如，将“时长正确、必要参与人空闲、会议室可用”命名为“可行候选”，后续可以集中比较可行候选的偏好。然而，名字本身没有消除复杂性。它的价值依赖定义稳定、调用方式明确，以及定义改变时能够知道哪些地方受影响。

## 类型为操作建立边界

时间是一个特别容易暴露语言问题的对象。一个没有时区的“上午九点”，一个确定的全球时间点，以及一段三十分钟的时长，都可以被存成数字或字符串，但它们能够参与的操作不同。

时长可以相加，某个时间点加时长可以得到另一个时间点；两个不同地点的本地时间，若没有日期和时区信息，就不能直接用于判断是否重叠。如果表示只记录数值，操作就需要不断猜测数值的含义。类型可以把这些差别明确地纳入表达规则。

同样，参与人的显示名称与账户标识也不同。两个同名的人可以拥有相同显示名称，却不是同一参与者；一份会议候选与已经建立的事件也不同。它们可能包含相似字段，但支持的操作和状态承诺不同。

类型检查能够提前排除某些没有定义的组合。例如，系统可以禁止把时长当作会议开始时刻，禁止把候选的临时编号当作已创建事件的标识。这种限制减少了执行时才发现错误的机会，也使调用方知道某个操作需要怎样的输入。

类型无法替代事实核对。一个时间值可以具有合法的类型，却对应错误的日期；一个对象可以被标成“必要参与人”，实际却是模型选错了身份。类型保证的是某些结构约定得到遵守，具体值是否符合现实仍有自己的证据要求。

对未知状态也需要这样的约定。日历读取失败，不意味着参与者空闲；一个参与者的可用时间尚未获得，也不应被随意转成“不参加”。表达体系需要说明缺失值怎样影响条件，哪些操作可以在未知存在时继续，哪些操作必须等待补充信息。

这里的设计不必追求一次覆盖所有状态。可以从真实出现、且导致不同后续动作的区别出发，让语言逐步拥有恰当的类型。每增加一种类型，都应该能说明它排除了哪类错误，或者支持了哪种原先含糊的操作。

## 同样能写程序为何还需要选择语言

假如一种通用编程语言足以实现会议助手，为什么还要讨论规则表达式、查询语言或某种小型 DSL？反过来，一旦设计了专门的规则语言，是否就应当把所有逻辑都放进去？

这两种选择都不能只靠“能不能表达”来决定。通用语言提供很大的实现空间，但一些重要的领域结构可能需要我们遵守额外约定才能被识别。专门的表达形式可以让某些关系直接出现，却也可能缺少实际任务所需的能力，并引入维护自身工具的成本。

Felleisen 在研究编程语言的表达能力时指出，比较可计算函数的集合不足以区分许多通用语言。他进一步研究某种构造能否通过保持结构的方式消去，以及翻译是否要求重组更大范围的程序。[Felleisen，1991](https://www.cs.tufts.edu/~nr/cs257/archive/matthias-felleisen/expressive-as-published.pdf) 这个视角提醒我们，表达能力还涉及结构如何被组织与保存。

在会议系统中，如果规则是一组明确的条件和偏好，程序可以分别找出未满足条件、比较候选或定位冲突。若同样的逻辑被包在任意函数里，这些分析仍可能实现，但需要额外约定、运行或分析方法。对于计算能力相同的语言，仍需比较它们如何保留程序结构，以及分析和维护需要付出什么成本。对于受限的领域语言，还应单独检查其表达范围是否覆盖任务需要。这些问题与某种构造能否在规定的结构保持翻译下被表达，有着不同的比较前提。

专门语言也有自身边界。只支持简单布尔条件，可能无法表达时间区间关系；缺少集合操作，可能迫使使用者手动展开参与人；没有清楚的状态语义，可能把“提出方案”和“建立事件”混为一谈。为每个特殊情形增加一个运算符，也可能使语言越来越难理解。

因此，选择表达形式可以从预期操作反推。若我们需要执行，表达必须有执行语义；若需要找冲突，重要约束要能被识别；若需要比较规则版本，变化应该对应可追查的结构；若需要开放的解释，原始语言材料也需要保留。自然语言、通用代码和领域表达可以共同承担这些工作。

实际选择可以从已有的查询、配置、逻辑或编程语言出发。采用已有形式，能够复用相应的工具和知识；设计新形式则应当说明已有形式在哪项关键操作上造成了具体困难。语言的收益需要连同生成、理解、执行与维护成本一起评价。

也可以只对任务中的一部分建立严格表达。例如，会议必须避免的日历冲突可以具有确定语义，而主题是否适合某位参与者，可以保留为带有依据的建议。两部分之间的连接需要清楚：建议怎样影响排序，是否能够推翻硬约束，哪些内容仍等待人的判断。这样，形式化的范围由实际需要决定，尚未明确的内容也有自己的位置。

## 从自然语言到 SQL 时真正需要确认什么

“找出每个部门收入最高的人。”这条查询看似简单，但至少有几个尚未固定的解释：部门按当前归属还是收入发生时归属计算；收入是工资、奖金还是某段期间的总额；并列最高是否全部返回；缺失收入是否参与比较。

假定我们已经确认只查询当前部门和一列明确的月收入，仍需处理并列。为单独观察并列处理，先假定参与排名的收入非空，并按部门分区，窗口内只按收入降序排序。若一个部门有两个人收入相同且最高，采用逐行编号后取第一行，与采用排名后返回所有第一名，会得到不同结果。PostgreSQL 对 row_number 和 rank 的定义正体现了这种差别：前者分配行号，后者使排序上的同等行获得同一排名。[窗口函数文档](https://www.postgresql.org/docs/current/functions-window.html)

两条查询都可以合法执行，也都可能在没有并列的数据上返回同样结果。因此，只拿一份普通数据测试，不能充分区分它们表达的要求。需要构造含有并列的例子，才能检查实现是否保留了已经确认的含义。

放宽收入非空的假设后，还会遇到缺失值的解释问题。SQL 中，普通比较运算遇到 NULL，通常得到未知，而非普通的真或假；判断是否为空需要相应的谓词。[比较运算文档](https://www.postgresql.org/docs/current/functions-comparison.html) 如果模型把“收入未知的人”转换成“收入为零的人”，代码可能继续运行，却改变了数据含义。

从这个例子看，自然语言转 SQL 至少需要三种相互配合的检查。首先确定任务中有关范围、并列和缺失值的解释；随后检查生成表达是否对应这些解释；最后检查数据和执行结果。语法正确只覆盖其中一部分。

反例在这里也具有特殊价值。一个例子可以专门检验并列处理，另一个检验空值，第三个检验跨部门范围。每个例子都有清楚的目的，并能帮助提出请求的人理解某项选择会导致什么后果。这些小例子让形式表达和人的意图保持可讨论的联系。

类似的方法也适用于会议助手。所有人都有空闲但没有共同空闲、所有候选都跨越某人的休息时间、某个日历尚未读取，这些情形分别检查量词范围、偏好取舍和未知状态处理。它们无需模拟整个生产环境，就能先暴露语言层面的分歧。

## 表达怎样在变化中保持含义

系统上线后，语言不会停止变化。团队可能重新定义必要参与人，新的工作习惯改变了对休息时间的判断，也可能增加“允许一位非必要参与人缺席”的条件。若这些变化只是散落在不同提示词中，同一个名称就可能在不同模块里逐渐拥有不同含义。

维护共同含义，需要让关键概念能够被定位和版本化。一项规则应当知道自己使用哪一版定义，某次结果应当能够回到当时的解释。这样，当“可行候选”的含义变化时，我们能够区分新任务按照新规则运行，与旧结果在旧规则下是否正确。

例子同样需要随定义更新。如果过去接受的安排现在应当被排除，测试的变化应当对应一个明确的要求变化，而非为了让新程序通过而调整答案。否则，验证会失去检验语言与意图是否一致的作用。

自然语言说明在这个过程中仍然重要。形式表达擅长固定已经选定的解释，原始说明和讨论记录则保存了为什么作出这种选择、有哪些尚未决的问题。两者结合，可以避免维护者面对一条精确规则，却无法理解它的适用理由。

还需要考虑组合时的冲突。两条规则分别合理，合在一起可能没有任何可行结果：一条要求所有人本地上午参加，另一条涉及跨越很远时区的参与者。语言可以把冲突表达得清楚，但解决冲突需要重新讨论约束、偏好或任务范围。增加计算预算不会自行决定谁的便利应当被让渡。

因此，语言也是协作的设施。它使分歧能够落在具体表达上，使约定能够被重复使用，使修改能够追踪到受影响的地方。人和系统不必在每次任务中重新猜测所有背景，但也需要保留修订约定的入口。

## 表达清楚之后仍然需要求解

回到开头的会议请求，现在我们可能已经明确了参与人、时间区间、时长、硬约束、偏好和当前动作。系统能够解释什么算可行，怎样比较方案，以及输出方案之后还需要什么进一步决定。

这些成果来自对语言的处理。它们没有保证已经找到合格时段。参与者的日历可能非常拥挤，候选数量也可能很多；当任务扩大为一天的研讨会，还会出现讲者冲突、房间安排和场次顺序等组合问题。

表达和求解因此可以互相连接，却不能彼此替代。表达决定什么算正确，求解寻找能够满足这些要求的对象。一个求解器可以忠实地找到某套条件下的最优解，如果条件误解了用户意图，最优性并不能修复这个误解。反过来，要求表达得非常清楚，也不会自动给出高效算法。

这一区分能帮助我们分析语言模型生成应用逻辑时的失败。若概念和组合范围尚未明确，就需要澄清或调整表达；若语义已经确定而候选搜索低效，就需要改变求解方法；若计算得到了满足规格的结果，现实使用仍然有问题，则还要检查规格与任务的联系。

语言的工程价值，体现在它使这些问题能够被分别提出。我们可以指出哪项要求被遗漏，哪个量词范围发生了变化，哪个状态不允许执行某个动作，以及哪个概念仍然需要讨论。应用由此获得了一种可以检查、协商和修改的共同形式。

当这份形式足够清楚，我们终于可以认真提出下一个问题：在有限时间和资源下，怎样找到一个足够好的答案？计算篇将从同一份会议要求出发，考察搜索、约束与资源分配怎样改变解决问题的过程。
