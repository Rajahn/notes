# 第六期 学习 怎样让经验成为可复用的能力

[返回系列目录](README.md)

## 同一个 bug，从头修了两遍

设想一组代码修复任务。一个数据接口用游标分页，协议允许中间某一页是空的：只要响应里还有下一页游标，调用方就该继续读。程序却把“这一页是空的”当成了“数据读完了”，于是漏掉了后面的记录。修复 Agent 读了调用代码，查了接口约定，构造了一个“空页之后还有数据”的测试，最后改对了结束条件。这次修得很好。

几天后，另一个服务出了类似的问题。函数名、响应字段、日志格式都换了，错误的核心没变：把一次局部观察当成了整个过程结束的信号。Agent 又从搜索报错开始，翻了一堆无关文件，慢慢找到分页循环，再把同类测试重新构造一遍。第二次也修好了。可第一次的工作，基本只留在了已经合并的代码里，没有改变它做下一道题的方式。

换更强的模型、加长上下文，都能让每次搜索更顺，却不回答一个问题：一次成功之后，系统到底得到了什么？它可能存下了全部对话，却没留下能调用的方法；可能记住了某个函数怎么改，却认不出别的项目里的同类结构；也可能总结出“遇到空页就继续”，再把它用到一个以空页表示结束的接口上。

所以谈学习，得把时间放进评价里：经历过这些任务，系统在后面的任务上做法变了没有，变化能不能持续，收益盖不盖得过获得经验的成本。

> 学习不看系统存下了多少，而看它在下一道题上的做法变了没有，变得值不值。

说成工程目标：用已有经验改变后续解题时的表示、选择或执行方式，在明确的质量要求下拿到能持续的收益，比如更少的搜索、更可靠的判断、更快适应新任务，或者更早发现某个方法不适用。它不必每次都更快，但要在关心的任务和时间范围里拿得出证据；存得更多、跑得更久、总结写得更长，都不算。

这样一来，一次修复就有了两个出口。一个是交付能用的修改；另一个是提炼出下次能用、能查、也能撤回的知识。系统的能力能不能随经历增长，看的是第二个出口。

## 记录、记忆和方法

先分开三样常被混在一起的东西。日志记下发生过什么：读过哪些文件，试过哪些补丁，哪些测试通过了。记忆让这些记录在需要时重新出现，比如检索到“这个项目的接口允许中间页为空”。方法则组织行动：碰到什么状态，先确认什么，接着做什么，什么时候停，凭什么认为结果可以接受。

分页案例的原始日志有几十轮搜索和大量偶然细节，原样塞进下一次的上下文，Agent 还得重新筛一遍。有用的记忆要留住接口约定、错误机制、有效修复和证据之间的关系。再往前一步就是方法：先找出协议规定的完成信号，再查循环有没有拿别的局部现象顶替它，最后把正常结束和异常停滞都验证一遍。这已经能指挥下一次的搜索了。

能学下来的也远不止一条答案。可以是概念和表征：“这页有没有数据”拆成“当前页内容”“有没有下一页”“是否读完”三个变量。可以是规则：这类协议里，是否结束由游标约定决定。可以是搜索策略：分页结果缺失，先查终止条件和游标推进。也可以是一段可执行程序，或者一次参数更新，改变模型选择这些行动的倾向。

形式不同，风险也不同。项目事实好核对，但管得窄；搜索顺序省时间，却可能让别的原因被忽略；程序执行稳定，但挑输入格式和权限；参数更新影响面广，出了问题也最难追到是哪条经验。选形式时要想清楚两件事：以后怎么用，出错了怎么查、怎么改。

DreamCoder 是一个清楚的研究实例：系统从解程序题的经验里学出可组合的符号抽象，同时训练一个引导程序搜索的模型。表达问题的语言和找解的策略，都成了学习对象。结果来自论文设定的程序归纳任务，带回工程的启发是：可以同时关注“学会用什么概念表达”和“学会怎样搜索”，别把学习等同于往库里追加事实。（[Ellis 等，2020](https://arxiv.org/abs/2006.08381)）

抽象也会出错。“空页未必意味着结束”留下了一个值得检查的可能；“空页从不意味着结束”却悄悄丢掉了协议这个前提。一次成功只支持当时验证过的关系，扩大适用范围得靠新任务和反例。把经验变成能力，最要紧的加工，就是留下那些看着啰嗦、其实决定结论成不成立的条件。

## 技能要有入口和出口

很多经验文档句句在理，真要执行，却答不出第一步该干什么。它们只写了原则，没写方法从哪儿进、从哪儿出。对要连续行动的系统，可复用的知识得具体到能回答三件事：现在该不该调用它，执行到哪里该停，停下之后交给下一步什么。

强化学习里的 options 框架，把一段跨越多个时间步的行为写成三部分：启动集合、内部策略和终止条件。行为可以根据中间状态随时调整，不必是一串固定动作。（[Sutton、Precup 与 Singh，1999，第 2 节](https://ics.uci.edu/~dechter/courses/ics-295/winter-2018/papers/Sutton-Precup-Singh-AIJ99.pdf)）它给了我们描述技能边界的骨架；某个 Agent 的技能库好不好用，还得放到真实的工具、权限、错误和验收里去检验。

拿“检查游标分页的终止条件”来说，可以分四步写清楚。

先是入口。启动条件要落在看得见的证据上：目标代码确实在遍历分页接口，问题表现为结果缺失或循环异常，而且找得到对应版本的协议约定。手里只有“结果少了”这一个现象时，这个方法只是一个待检验的排查方向，不能据此跳过过滤条件、权限范围这些可能，直接去改循环。

然后是执行。定位状态变量，对照协议和实现，构造能区分几种解释的输入。测试要覆盖协议真正允许的边界：协议同时允许“空页但有下一页”和“非空页但没有下一页”，两种状态就都要出现，否则靠数据条数猜结束的实现在普通样例里照样能过。协议允许重复游标作为特殊状态，就按协议处理；不允许，检测到重复就报告异常，而不是悄悄中断、装作读完了。

再是出口，完成和受阻要分开。读到协议规定的结束状态，可以宣布遍历完成；碰到确认不了的接口版本、超出调用预算、复现不了的问题，就退出，并把不确定性交出去。两种出口都合理，交给下一步的信息却不同。一个只会返回“执行完毕”的技能，会让后面的系统把“没继续做”读成“已经做对了”。

最后是验收。测试要覆盖原来的失败，也要覆盖正常结束、游标推进和异常处理，并确认没有把有限的请求变成死循环、没有吞掉原有的错误信号。测试通过只支持测试和协议覆盖到的范围，技能记录要写明这个范围，以及它依赖的接口版本和关键假设。

这样的技能比一句“检查分页逻辑”长，调用者要重新猜的却少多了：下一个 Agent 继承一个搜索入口、一组判别实验和一套退出方式，再按新项目调整实现。复用的就是这套经过解释的决策结构；文件名、工具、协议参数这些会变的东西，调用时再绑定。

## 整体被拒，局部可留

真实任务里的改进常常一整包交上来。假设 Agent 为修分页问题同时提交了三处修改：修正终止条件、缓存接口响应、把异常转成空结果。整体验收没过：缓存带来了过期数据，异常处理掩盖了故障。只记下“这个候选失败”，正确的终止条件修复也跟着丢了；只记下成功的样例，又可能把危险的配套修改带进下一次。

更合适的保留单位，是有独立证据支持的那一处变化。先把三处修改拆开，确认终止条件的修复在没有新缓存、不吞异常时仍然成立，再查组合后才出现的问题。能独立留下的不只是补丁，也可以是失败的复现、对协议的解释、测试的构造方法。某个片段依赖候选里的其他改动，就把依赖一并记下，不能因为局部代码看着对就说它安全。

反馈也要落到能调整的对象上。“验收未通过”只说明整体失败；“空页后仍有游标的案例已修好，但响应过期让另一类请求读到了旧数据”，才能指导系统留下第一处、撤回第二处、改掉缓存策略的适用条件。反馈的价值，在于分清哪些假设被支持，哪些被推翻，哪些还没查到。

失败记录同样要加工。一次超时不等于方法无效，可能只是预算不够；一次测试通过也可能靠环境碰巧满足了某个条件。把现象直接写成规则，等于把没做完的归因固化成长期行为。值得留下的记录，要连起输入状态、采取的行动、观察结果和当前解释，并允许后来的证据改写解释，而不是只贴一个“成功”或“失败”的标签。

能拆多细，取决于执行时留下了多少。所有改动都在一条无法复现的长轨迹里完成、中间状态没有记录，就拆不出各自的贡献。想让系统学到局部成果，行动时就得留下版本、输入和验收依据：可学习性反过来要求执行过程可观察。

任务结束后，有证据支持的片段进候选知识库，有价值但证据不足的想法放进待验证区，已知不适用的条件记成限制。候选库不是发布库：一次局部成功只是继续检验的理由，能不能跨任务复用，要由后面的任务来定。

## 学习也要记账

学习常被说成免费的积累：多存点经验，总有用得上的时候。可提炼、验证、检索、维护都要花资源：经验越多越难挑对，方法越通用，调用前要确认的条件越多，用错了还要返工。哪怕后面每次都少走几步，维护太贵也可能得不偿失。

所以要算整个使用周期的账。假设两种方案达到同样的验收要求：一种每次从头解，另一种先获得一个方法，再拿去处理后面的任务。后者的总成本可以这样记：

```math
C_{\text{复用}}(N)=B+M+\sum_{i=1}^{N}(R_i+E_i+V_i+F_i)
```

B 是获得方法的成本，包括提炼和首次验证；M 是比较周期内的维护成本，比如跟着版本修订；每个任务上，R 是检索和判断是否适用，E 是执行，V 是验收，F 是误用带来的额外检查和返工。这个式子只为防止漏账；具体项目里，延迟、计算费用和人的注意力可能要分开报告，不该不加说明就压成一个数。

拿分页检查这项技能代入一组构造的数字。在固定的评价周期里，获得它花 120 个成本单位，维护花 30；之后每个适用任务平均检索和判断 1、执行 3、验收 3、误用返工 1，合计 8。对照方案每次从头处理要 15，已经包含同样质量要求下的验收和返工。于是复用方案的预期成本是 150＋8N，对照是 15N。适用任务出现 30 次时，两者分别是 390 和 450；只出现 10 次时，是 230 和 150。在这组假设下，要到第 22 次，前期投入才算摊平。

结论跟着任务频率、适用率和错误率走：技能很少被调用，提炼可能收不回成本；检索常挑错技能，F 就会涨；环境变得快，M 也会变。实际比较要用两种方案面对的同一批任务，把没调用、调用后放弃、调错再回退的路径都记进去，不能只挑复用成功的任务算节省。

质量也不能从账本上消失。省了搜索却漏掉更多错误，不算学习有效；质量和成本有交换，就把交换关系摆出来。把获得成本全藏进离线阶段，同样会高估收益：离线学习可以值得，理由要来自未来的使用规模和质量收益。

这样一算，“值得学什么”就成了具体问题。高频、结构稳定、验证清楚的任务，适合早点沉淀成方法；低频、变化大的任务，也许只保存原始证据和检索入口更划算。系统要学的不只是怎么做，还有什么时候值得为一条经验付抽象和维护的成本。

## 经验也会帮倒忙

复用会把过去的判断带进新环境。假设分页技能来自一种允许空中间页的游标协议，新任务用的却是偏移量分页，协议明确规定空页就是结束。如果检索只看“分页”“结果缺失”这些词，就可能调出错误的结束规则。这就是负迁移：旧知识让新任务更贵、更容易错，从头检查协议反而可能做得更好。

办法是把“适用”当成一个待确认的关系。项目、接口版本、协议类型、验证过的边界，都应该是检索和调用的依据；名字相似可以帮着找到候选，替代不了结构匹配。在新环境里，一个方法先是一个假设：它预测什么，有什么证据支持，怎样用最小的代价发现它不适用？

经验还会过期。依赖升级后，接口的错误语义变了，旧技能的步骤照样能跑，结论却不再可靠。稳妥的做法是记下依赖，相关版本一变就重新验证或降低调用优先级；确认不了状态的知识先隔离，比默默沿用好追查。旧版本也要留着，用来解释历史任务当时为什么那样做。

遗忘要分两种。参数更新后丢了仍然重要的能力，要检测和补救；主动清掉过期、重复、收益很低的经验，反而让检索和维护更轻松。删一条记录和丢一种能力并不一一对应：几条记录可能说的是同一个方法，一条冷门的限制也可能挡住一次严重误用。清理要看依赖和实际作用，不能只按调用次数定去留。

有时候，失败要求改的是概念本身。知识库起初可能把所有分页问题都归进“循环结束错误”，后来才发现“结束状态不明确”“游标没有推进”“遍历期间数据变了”需要不同的证据和修法。继续往大类下面追加例外，方法只会越来越难调用；拆开概念、重划边界，经验才能各归其位。概念一改，旧结论也要跟着动：一个标成“分页终止修复成功”的案例，可能只解决了固定数据集上的结束问题，没覆盖数据变化时的完整性，就该收窄声明、补上验证。所以知识库要能修订、能撤回；只追加、不改写的积累，跟不上理解的变化。

## 拿没见过的题来考

经验有没有变成能迁移的能力，得拿没见过的题来考。同一段代码改个函数名，交给手握原答案的系统，分不清它是学会了方法还是认出了旧答案。隔离要按想检验的迁移范围设计：跨文件，检查局部复用；跨项目，检查能否认出同类结构；跨协议，检查适用性判断够不够谨慎。

做法是固定一组用来积累经验的任务，冻结方法库和调用策略，再在独立任务上比较有无经验的表现。对照用相同的基础能力、工具权限和任务预算；学习方案多花的前期计算一并报告。用来改进方法的评价案例都算“见过”，不能再当最终考题；相关项目、重复缺陷、相似模板也会造成泄漏。

考题里还要放不该用这项技能的题。只考游标分页，看得到技能怎么执行，看不到它会不会在偏移量分页、权限过滤、缓存故障里被误用。真实任务流里，适用、相近和无关的问题混在一起，不调用、及时退出、换方法，都是要观察的能力。一项经验替适用任务省了多少、给其他任务添了多少负担，要放在一起看。

还要看新能力有没有挤掉旧能力。持续学习研究明确把跨任务迁移和已有能力的保持都纳入评价，而不只看当前任务的准确率。（[Lopez-Paz 与 Ranzato，2017](https://arxiv.org/abs/1706.08840)）工程上可以借用这个问题：定期回放一组仍然重要的旧任务，看参数更新、方法库扩张或检索策略调整有没有带来退化。

最后，有两种收益容易混为一谈。一种是同类任务更好做了：学会了分页检查，下次少翻几轮代码。另一种是学新任务更快了：碰到从没处理过的流式协议，能借用已有的状态、终止和验证概念，用更少的样例学会新方法。前者是复用收益；后者要看适应过程，比如达到同样质量需要多少次反馈、多少总成本。单次成功分不出这两种。可以让系统面对多个新的任务族，在相同的反馈和资源约束下记录学习过程，同时检查旧任务。结果可能是熟悉的模式更快、陌生的模式没有优势，也可能更会提验证问题、执行成本却还很高。这样拆开看，比一个综合得分更能说明下一步该改表示、检索、执行还是反馈。

## 记住答案，还是学会配方

人学数学是个方便的对照。不谈普遍的认知规律，只看同一道题能留下什么：解完一个二次式，可以记住这次的数值答案，可以记住配方的步骤，也可以理解配方怎样把一般形式变成能直接看出性质的形式。最后一种收获会改变下次看题时注意到的结构，但它同样要在新题里用过才算数。

下一题只换了系数，套步骤也许就够；改成讨论参数范围，就得明白中间那步变换保留了什么；变量和约束都变了，方法可能还要调整。一道题的经验，可能留下一条执行路线，也可能改变问题的表示方式，以及哪些变换值得一试。分页案例里也有这三层：记住某个函数怎么改，记住一套排查步骤，以及把“这页有没有数据”拆成三个变量。

## 回到开头

分页这个例子，其实把六篇都走了一遍。把“这页有没有数据”拆成三个变量，是表征；把协议约定和技能边界写成其他组件也能用的明确条件，是语言；安排排查顺序、调用预算和退出时机，是计算；判断测试通过究竟支持了什么，是认识；从被拒的候选里分清哪处修改真正有效，是因果与实验。学习把这些环节接到未来的任务上，让一次任务的结果，参与下一次任务的开头。

这个循环有时增长能力，有时只增长复杂度。分清两者，要一直记着目标：系统到底要完成什么，哪些错误不能接受，什么成本值得付，哪些问题还没有证据。更长的记忆、更大的技能库、更频繁的更新，都回答不了这些问题；目标一变，攒下的能力也要重新衡量。所以人仍要参与选目标、改概念、划定证据的边界，落到实处，就是明确的验收要求、能被追问的经验记录和对新问题保持开放的分类。系统说得清自己继承了什么、何时调用、哪里还缺证据，团队才能接着改它，不用每次失败后重新猜。

回到开头的代码修复。下一次遇到结果缺失，值得期待的是：Agent 早早想到终止语义，先确认当前协议，选有区分力的测试，不适用时及时退出，留下能被检查的结果。这些具体行为，才让上一次修复变成了后来能用的能力，也成了下一轮学习的起点：哪些判断已经可靠，哪些方法该收窄，哪些问题还得重新理解。

把这一篇压缩成可以带回项目的检查，大致是四个问题：

1. **下一道题，做法变了吗？** 在没参与修订的新任务上和无经验的对照比较成功率、总成本、尝试次数，同时回放旧任务看有没有退化。
2. **经验有入口和出口吗？** 什么证据下才调用，完成和受阻是否分开报告，验收覆盖了哪些边界，依赖哪个版本。
3. **账算全了吗？** 获得、维护、检索、误用都记进去，在同一批任务上和从头做的方案比，而不是只数复用成功的那几次。
4. **它知道什么时候不该被用吗？** 混进相近但不适用的任务，看它会不会误用、能不能退出；版本一变，是否触发重新验证。

六篇读下来，检查的对象一直在变，问题却是同一个。第一期开头，那次黎曼猜想的 Lean 核验在检查证明之前，先确认了“题目是不是这道题”；第一期的核心检查，是看两份本应不同的材料，有没有在接口里变成同一份数据。之后我们依次追问：区别有没有被明确地表达，能不能以合理的成本求解，判断凭什么成立，改动凭什么有效。到了学习，这些问题被放进了时间里：每一次带着旧经验出发，都要先问一句，眼前这道题，还是不是上次那道题？

模型的能力怎样变成系统能反复使用的能力？不靠某一次漂亮的成功，而靠系统把每次成功留成下一次可以调用、可以检查、也可以撤回的东西。
