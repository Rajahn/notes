# 第六期 学习 怎样让经验成为可复用的能力

[返回系列目录](README.md)

## 回答一次与获得一种能力

设想一组代码修复任务。一个数据接口使用游标分页，协议允许中间某页没有记录，只要响应里仍有下一页游标，调用方就应继续读取。程序却把“当前页为空”当成“全部数据已经读完”，因此漏掉了后面的记录。修复 Agent 阅读调用代码、查看接口约定、构造空页后仍有数据的测试，最后改正了结束条件。这次任务完成得很好。

几天后，另一个服务出现类似问题。函数名、响应字段和日志格式都变了，核心错误仍是把局部观察当成整个过程的终止信号。Agent 再次从搜索报错开始，检查大量无关文件，逐步找到分页循环，又重新构造了一遍同类测试。第二次也修好了，可第一次工作的价值主要停留在已经合并的代码里，没有明显改变它解决下一道题的方式。

我们可以继续增加模型能力，让每次搜索都更顺利，也可以延长上下文，把更多历史放进去。但这里还有一个独立的问题：一次成功之后，系统究竟获得了什么？它可能保存了全部对话，却没有留下可调用的方法；可能记住了某个函数的修改，却无法认出另一个项目里的同类结构；也可能总结出“遇到空页就继续”，随后把这条经验错误地用到以空页表示结束的接口上。

讨论学习，需要把时间放进系统的评价方式。一次任务的表现，告诉我们系统在当时的条件下做到了什么。学习则要求进一步观察：经历这些任务之后，它在后续任务上的行为发生了什么变化，这种变化能否持续，收益能否覆盖获得经验的成本。保存得更多、运行得更久、生成了更长的总结，都不能单独回答这个问题。

在本文里，我们把学习理解为一个可检验的工程目标：利用已有经验，改变后续解决问题的表示、选择或执行方式，并在明确的质量要求下获得可持续的收益。收益可以是更少的搜索、更可靠的判断、更快地适应新任务，也可以是更早识别某种方法不适用。它不必表现为每次都更快，却需要在关心的任务范围和时间范围内得到证据支持。

这让一次修复有了第二个出口。一个出口是交付可用的修改；另一个出口是提炼出下一次能够使用、能够检查、也能够撤回的知识。后一个出口，决定了系统的能力能否随着经历增长。

## 经验可以改变哪些东西

先区分三种容易混在一起的东西。日志保留“发生过什么”：读过哪些文件，尝试过哪些补丁，哪些测试通过。记忆让这些记录在需要时重新出现，例如检索到“这个项目的接口曾经允许空的中间页”。方法则进一步组织行动：面对什么状态，先确认什么，接着做什么，在什么条件下停止，以及凭什么判断结果可接受。三者可以互相支持，但各自承担的工作不同。

分页案例里的原始日志，可能有数十轮搜索和许多偶然细节。若将它原样放进下一次上下文，Agent 仍要重新完成筛选与抽象。一个更有用的记忆，应该保留接口约定、错误机制、有效修复及其证据之间的关系。方法则可以概括为：先识别协议规定的完成信号，再检查循环是否用其他局部现象替代了它，最后同时验证正常完成和异常停滞。这已经能引导新任务中的搜索。

学习对象因此远比一条答案丰富。它可以改变概念和表征：原先只有“页面有数据或无数据”，后来区分“当前页内容”“是否存在后继”“读取是否完整”三个变量。它可以形成规则：某类协议中，完成状态由游标约定决定。它可以调整搜索策略：看见分页结果缺失时，优先检查终止条件和游标推进。它也可以形成一段可执行程序，或通过参数更新改变模型选择这些行动的倾向。

这些对象的收益和风险不同。一条项目事实容易核验，但作用范围较窄；一个搜索顺序能够节省时间，却可能让其他原因被忽略；一段程序执行稳定，但对输入格式和权限有要求；参数更新可能影响较广，也较难把某次行为变化直接定位到一条经验。选择保存形式时，要同时考虑未来怎样使用它，以及出问题后怎样追查和修正它。

DreamCoder 提供了一个明确的研究实例：系统从程序求解经验中学习可组合的符号抽象，同时训练引导程序搜索的模型。可用于表达问题的语言和在其中寻找解的策略，都成为了学习对象。这个结果来自论文设定的程序归纳任务；它给工程设计的启发，是可以同时关注“学会用什么概念表达”和“学会怎样搜索”，而不把学习等同于追加事实。（[Ellis 等，2020](https://arxiv.org/abs/2006.08381)）

抽象也会出错。“空页未必终止”保留了一个值得检查的可能性；“空页从不终止”却悄悄丢掉了协议前提。一次成功只能支持当时经过验证的关系。要扩大适用范围，需要新的任务和反例提供依据。把经验变成能力时，最重要的加工之一，就是保留那些看起来啰嗦、实际决定结论是否成立的条件。

## 给方法写出可调用的边界

许多经验文档读起来很有道理，真正执行时却无法回答第一步该做什么。原因通常在于，它描述了理想原则，没有定义方法的入口和出口。对于一个需要连续行动的系统，可复用知识需要足够具体，使系统能判断现在是否适合调用，执行到哪里应当停止，以及结束后有哪些可供后续步骤使用的结果。

强化学习中的 options 框架，把一段跨越多个时间步的行为描述为启动集合、内部策略和终止条件。行为可以根据中间状态持续调整，而不必是一串固定动作。这个形式提供了一种理解技能边界的方式，但不能直接证明某个 Agent 的技能库有效；实际实现仍需处理工具、权限、错误和验收。（[Sutton、Precup 与 Singh，1999，第 2 节](https://ics.uci.edu/~dechter/courses/ics-295/winter-2018/papers/Sutton-Precup-Singh-AIJ99.pdf)）

以“检查游标分页终止条件”为例，启动条件应该包含可观察的证据：目标代码确实遍历分页接口，当前问题涉及结果缺失或循环异常，而且可以找到对应版本的协议约定。如果目前只有“结果少了”这一现象，方法可以作为一个待检验的排查方向；系统不能据此跳过过滤条件、权限范围等其他可能原因，直接开始改循环。

执行过程可以先定位状态变量，再比较协议与实现，随后构造能够区分竞争解释的输入。测试需要覆盖协议实际允许的边界。例如，在同时允许“空页且有后继”和“非空页且无后继”的协议中，应让这两种状态分别出现，否则一个用数据数量猜测结束的实现，仍可能在普通样例里过关。若协议允许重复游标作为特殊状态，就按协议处理；若不允许，检测到重复时应报告异常，不能将主动中断伪装成完整读取。

终止还需要区分任务完成与执行受阻。读取到了协议规定的结束状态，可以声明遍历完成；遇到无法确认的接口版本、超过调用预算或无法复现的问题，则应退出并保留不确定性。两种出口都可以是合理行为，但它们交给下一步的信息不同。一个只返回“执行完毕”的技能，会让后续系统把“没有继续做”误读为“已经做对”。

验收条件进一步约束方法是否真的奏效。修复后的测试应覆盖原来的失败，也应覆盖协议中的正常结束、游标推进和异常处理；需要检查它没有把有限请求变成无限循环，没有漏掉已有错误信号。测试通过仍只在测试和协议覆盖的范围内提供支持。技能记录应保留这个范围，以及它依赖的接口版本和关键假设。

这样的技能会比一句“检查分页逻辑”长一些，但它减少了调用者需要重新猜测的内容。后续 Agent 可以从中继承一个搜索入口、一组判别实验和一套退出方式，同时根据新项目调整实现。复用的核心由此变得具体：保留经过解释的决策结构，让变化的文件名、工具和协议参数在调用时重新绑定。

## 被拒绝的候选也能留下成果

真实任务中的改进往往以一个整体候选出现。假设 Agent 为修复分页问题同时提交三项修改：修正终止条件、缓存接口响应、把异常转换为空结果。整体验收失败了，因为缓存引入了过期数据，异常处理又掩盖了故障。如果系统只保存“这个候选失败”，正确的终止条件修复也可能一起消失；如果只保存其中一个成功样例，又可能把危险的配套修改带到下一次。

比较有效的保留单位，是有独立证据支持的变化。先把三个修改拆开，确认终止条件修复在没有新缓存和异常吞噬的情况下仍然成立，再检查组合后才出现的问题。能够独立保留的，既可以是补丁，也可以是失败复现、协议解释或测试构造方法。若某个片段依赖候选中的其他变化，就要连同依赖一起记录，不能仅凭局部代码看起来正确便宣称安全。

反馈也应回到能够调整的对象。“未通过验收”只能让系统知道整体失败；“空页后仍有下一游标的案例已修复，但响应过期导致另一类请求读到旧数据”，才可能指导它保留第一项、撤回第二项，并修改缓存策略的适用条件。反馈的价值取决于它能否区分哪些假设被支持，哪些假设受到反驳，还有哪些地方没有被检查。

失败记录同样需要加工。一次超时不等于方法无效，可能只是预算不足；一次测试通过也可能依赖环境偶然满足的条件。将现象直接固化成规则，等于把尚未完成的归因写进长期行为。值得保留的记录应当连接输入状态、采取的行动、观察结果和当前解释，并允许后续证据修改解释，而不是只留下一个成功或失败标签。

这里还有一个容易忽略的限制：局部证据的颗粒度，决定了我们能保留多细的成果。如果所有变化都在一个无法复现的长轨迹里完成，又没有记录中间状态，就很难可靠地拆出贡献。让系统学习局部成果，需要在行动时留下必要的版本、输入和验收依据。可学习性因此会反过来要求执行过程具备合适的可观察性。

完成一次任务之后，可以将已被支持的片段纳入候选知识库，把有价值但证据不足的想法留在待验证区，把已知不适用的条件记录为限制。进入候选库并不意味着立刻广泛调用。一次局部成功提供了继续检验的理由；跨任务复用的资格，还要由后续任务来决定。

## 学习要支付什么成本

学习经常被描述为免费的积累：多保存一些经验，未来总会有用。但提炼、验证、检索和维护都要消耗资源。经验越多，选择正确经验可能越困难；方法越通用，调用之前要确认的条件可能越多；错误复用还会带来返工。一个系统即使后续每次执行都少走几步，也可能因为维护成本过高而得不偿失。

因此需要比较整个使用周期。假设两种方案达到相同的验收要求，一种每次从头求解，另一种先获得一个方法，再用于后续任务。可把后者的总成本写成下面的记账方式，其中获得成本包括提炼和首次验证，维护成本包括后续版本修订，误用成本包括错误调用引起的检查和返工。

```math
C_{\text{复用}}(N)=B+M+\sum_{i=1}^{N}(R_i+E_i+V_i+F_i)
```

这里，B 是获得方法的成本，M 是所比较周期内的维护成本，R 是检索与适用性判断，E 是执行，V 是验收，F 是误用带来的额外成本。这个式子只是帮助防止漏账；具体项目里，延迟、计算费用和人的注意力可能需要分别报告，不能未经说明就压成同一个数字。

用一组构造数字说明。假设在固定的评价周期里，获得方法花费 120 个成本单位，维护花费 30；后续每个适用任务平均需要检索和判断 1、执行 3、验收 3、误用返工 1，合计 8。对照方案每次从头处理需要 15，包含相同质量要求下的验收与返工。于是，复用方案的预期成本为 150＋8N，对照为 15N。遇到 30 次适用任务时，分别为 390 和 450；只遇到 10 次时，则为 230 和 150。在这些假设下，要达到 22 次，前期投入才被摊平。

这个结论依赖任务频率、适用率和错误率。若某项技能很少被调用，精心提炼可能没有回报；若检索经常选错技能，误用成本会增加；若环境快速变化，维护成本也会改变。实际比较应以两种方案面对的同一批任务为单位，把未调用、调用后放弃、错误调用再回退的路径一起记入，不能只挑选复用成功的任务计算节省。

质量也不能从成本表里消失。方法省下搜索却漏掉更多错误，无法直接宣布学习有效；如果质量和成本存在交换，就应展示交换关系，并说明当前任务允许怎样取舍。把获得成本全部隐藏到离线阶段，同样会高估收益。离线学习可以值得投入，但投入的理由应来自未来的使用规模和质量收益。

这类记账让“值得学什么”成为一个具体问题。高频、结构稳定、验证清楚的任务，适合较早形成方法；低频且变化大的任务，可能更适合保存原始证据和检索入口。系统需要学习的不只是行动方法，还包括何时值得为一种经验支付抽象和维护的成本。

## 怎样防止经验变成负担

复用会把过去的判断带进新的环境。假设分页技能来自一种允许空中间页的游标协议，而新任务使用的是以空页明确表示结束的偏移量协议。如果检索只根据“分页”“结果缺失”等词匹配，就可能调用错误的结束规则。这里发生的负迁移很具体：过去有用的知识，增加了新任务的成本或错误，而系统原本从头检查协议可能会做得更好。

减少这种问题，需要把经验的适用性看作待确认的关系。项目、接口版本、协议类型和验证过的边界，都应成为检索和调用的依据。相似名称可以帮助找到候选，不能替代结构匹配。一个方法在新环境里应该先被当成假设：它预测什么，哪些证据支持这个预测，怎样用较小代价发现不适用？

经验也可能只是在时间中失效。依赖升级之后，接口的错误语义改变了，旧技能的步骤仍能执行，结论却不再可靠。较稳妥的设计是记录依赖，并在相关版本变化时触发重新验证或降低调用优先级。对无法确认状态的知识，暂时隔离比默默沿用更容易追查。保留旧版本还有一个作用：解释历史任务当时为什么采取了那个动作。

遗忘也需要区分不同情形。系统更新参数后丢失了仍然重要的能力，需要检测和补救；系统主动移除过期、重复或收益很低的经验，则可能改善检索和维护。删除条目与失去能力之间没有简单对应关系：多个条目可能表达相同方法，一条看似冷门的限制也可能防止严重误用。清理时应检查依赖和实际作用，不能只按调用次数决定去留。

有时，失败要求修改概念本身。最初的知识库可能把所有分页问题归入“循环结束错误”，后来才发现“结束状态不明确”“游标没有推进”“数据在遍历期间变化”需要不同证据和修复。继续往一个大类别下面追加例外，会使方法越来越难调用。拆分概念、重新组织边界，反而能让已有经验获得更准确的位置。

这种修订也会影响过去的结论。一个被标记为“分页终止修复成功”的案例，可能只解决了固定数据集中的结束问题，没有覆盖数据变化时的完整性。重新分类能够提醒系统收窄声明，并寻找缺失的验证。知识库因而需要允许修订和撤回；只有追加、没有改写的积累方式，很难跟上理解的变化。

## 在没有见过的问题上检查学习

若要判断经验是否形成了可迁移能力，需要给系统尚未见过的问题。若把同一段代码改个函数名，再让拥有原始答案的系统作答，很难判断它获得了可迁移方法，还是认出了已有解。任务隔离应根据想验证的迁移范围设计：跨文件可以检查局部复用，跨项目可以检查结构识别，跨协议则能够检查适用性判断是否足够谨慎。

可以先固定一组用于获得经验的任务，再冻结方法库和调用策略，在独立任务上比较有无这些经验的表现。对照应使用相同的基础能力、工具权限和任务预算；若学习方案消耗了额外的前期计算，就同时报告这笔投入。任何用于改进方法的评价案例都应进入已见数据，不能继续充当最终检验。相关项目、重复缺陷和相似模板也需要考虑泄漏问题。

评价还应该包含不适用的任务。只安排游标分页问题，能够检查技能怎样执行，却不能检查系统会不会在偏移量分页、权限过滤或缓存故障中误用它。现实的任务流混合了适用、近似和无关问题。让系统选择不调用、及时退出、转向其他方法，都是需要观察的能力。每项经验省了多少成本，与它给其他任务增加了多少负担，应放在一起看。

还要检查新能力是否挤掉了旧能力。持续学习研究明确把跨任务迁移和已有能力的保持纳入评价，而不只看当前任务的准确率。工程上可以借用这个评价问题，定期回放一组仍然重要的旧任务，观察参数更新、方法库扩张或检索策略变化是否带来退化。（[Lopez-Paz 与 Ranzato，2017](https://arxiv.org/abs/1706.08840)）

这里有两个容易混淆的目标。第一个是后续同类任务更容易解决：已经学会分页检查，因此少查几轮代码。第二个是学习新的任务更快：遇到从未处理的流式协议，系统能够利用既有的状态、终止和验证概念，以更少样例获得新方法。前者证明了复用收益，后者需要观察适应新任务的过程，例如达到相同质量所需的反馈次数和总成本。

单次成功无法区分这两者。可以让系统面对多个新的任务族，在相同反馈和资源约束下记录学习过程，并同时检查旧任务能力。结果可能是它对熟悉模式更快，对新模式没有优势；也可能更善于提出验证问题，却仍需要大量执行成本。这样的分解比一个综合得分更能解释下一步应改表示、检索、执行还是反馈。

## 让经验重新进入理解的循环

人的数学学习提供了一个便于思考的例子。这里不讨论普遍的认知规律，只比较同一道题可能留下的不同内容。解出一个二次式后，可以记住这次的数值答案，也可以记住配方步骤，还可以理解配方如何把一般形式转成能够直接观察性质的形式。最后一种收获会改变下一次看题时注意到的结构，但它仍需通过新问题中的使用来检验。

如果下一题只有系数变化，套用步骤可能足够；若问题改成讨论参数范围，就需要理解中间变换保留了什么；若变量和约束改变，原方法还可能需要调整。这个例子把知识、程序和概念联系起来：一道题的经验，既可能留下执行路线，也可能改变问题怎样被表示，以及哪些变换被认为值得尝试。

对工程系统而言，学习同样会把我们带回系列的起点。新的经验可能要求增加一个状态变量，形成新的表征；为了让它被其他组件使用，需要用明确的语言写出关系和边界；执行它需要分配计算资源；判断它是否有效，需要观察与验证；决定究竟保留哪一项变化，需要实验与归因。学习把这些环节连接到未来的任务，使一次任务的结果能够参与下一次任务的开始。

这个循环有时增长能力，有时只增长复杂度。判断两者的区别，需要始终保留目标：我们究竟希望系统完成什么，哪些错误不可接受，什么成本值得支付，哪些问题仍然没有证据。更长的记忆、更大的技能库和更频繁的更新，本身都不能替我们回答这些问题。评价目标发生变化时，过去积累的能力也需要重新衡量。

人仍需要参与目标的选择、概念的修订和证据边界的判断。这种参与可以落实为明确的验收要求、能够追问的经验记录，以及对未知问题继续开放的分类方式。一个系统能解释自己继承了什么、何时会调用、哪里还缺证据，团队才更容易接着改进它，而不必在每次失败后重新猜测内部发生了什么。

回到开头的代码修复。下一次遇到结果缺失时，值得期待的变化是：Agent 较早识别出可能的终止语义问题，主动确认当前协议，选择有区分力的测试，在不适用时退出，并留下足以检查的结果。这些具体行为，才让先前那次修复延伸成后续可用的能力。它们也给下一轮学习提供了新的起点：哪些判断已经可靠，哪些方法应该收窄，哪些问题还需要重新理解。
