# 第 1 章　问题定义与设计目标

本章回答四个问题：这套系统要解决什么问题；它产出什么；它追求什么、明确不追求什么；以及贯穿全部子系统的几条设计原则。后面各章讲的每一个机制，都可以追溯到本章的某条目标或原则。

## 1.1 要解决的问题

### 1.1.1 一类常见的业务判定

很多业务判定有相同的形状：输入是一份材料（买家的文字描述、上传的图片、订单的结构化字段），输出是一个有限取值的结论（受理、拒绝、转人工；卖家责任、买家责任、超出时限）。这类判定有三个共同特点：

1. **结论依赖对材料的理解。** "商品是否腐烂变质"要读懂描述或看图，不能只靠结构化字段。
2. **结论受政策约束。** 同样的事实在不同政策下结论不同，例如时限从 48 小时改为 72 小时。政策需要能被业务方看懂、审核和修改。
3. **错误有代价，而且代价不对称。** 把卖家责任判成买家责任，和反过来，业务后果不同；拿不准时转人工，也有人工成本。

### 1.1.2 三种常见做法及其问题

| 做法 | 优点 | 问题 |
|---|---|---|
| 人工编写规则，结构化字段直接判断 | 规则清楚、可审核 | 读不懂文字和图片；靠关键词匹配时，换一种说法就失效 |
| 训练一个黑盒分类模型 | 能利用材料中的复杂信号 | 规则不可见，政策调整要重新训练；出错时无法定位是"没看懂"还是"规则不对" |
| 让大语言模型直接给出结论 | 不需要训练，能读懂材料 | 政策写在提示里，很难验证它是否被遵守；同一份材料多次询问可能给出不同结论；无法审计"依据哪条事实得出结论" |

### 1.1.3 本系统的做法：事实与政策分离

本系统把一个判定拆成两层，写在同一份完整的程序里：

- **事实层**：用模型回答**封闭的事实问题**，例如"描述是否明确指向腐烂、发霉或变质"，选项是"是、否、无法判断"。模型的回答按概率阈值解码成一个值。
- **政策层**：用显式规则把事实组合成结论，例如"超出时限 → 超出时限；否则腐烂 → 卖家责任；否则 → 买家责任；事实无法确定 → 转人工"。

这份程序用作者语言 `v5-author/1` 编写，由执行服务求值。系统要做的事情，就是**得到一份好的这样的程序，并持续把它改得更好**：

- 问哪些事实、怎样问（问题文本、选项说明、解码阈值）；
- 怎样把事实组合成结论（规则）；
- 以及在改动之后，用真实执行证明改动确实更好、而且没有破坏原来做对的案例。

## 1.2 贯穿全书的例子：生鲜售后定责

这个例子来自仓库的作者语言文档（`engine/docs/authoring.md`），本书后续章节都会回到它。

**场景**：买家对生鲜订单发起售后。输入是签收后经过的小时数和买家的文字描述。结论有四种：`OUT_OF_WINDOW`（超出售后时限）、`SELLER_DUTY`（卖家责任）、`BUYER_DUTY`（买家责任）、`MANUAL`（转人工）。

**程序的结构**（节选，省略了 `dsl` 版本、`types` 中的结论枚举和各定义的类型标注，完整写法见仓库文档）：

```json
{
  "authoring": "v5-author/1",
  "id": "fresh-duty",
  "inputs": {"hoursSinceDelivery": "Integer", "description": "Text"},
  "params": {"windowHours": 48},
  "effects": {
    "rot": {
      "$read": "jev@1",
      "binding": {
        "request": {
          "model": "example-model@1",
          "questions": {"rot": {"type": "choice",
            "instructions": "根据买家描述判断商品是否腐烂变质",
            "criteria": {"yes": "描述明确指向腐烂、发霉或变质",
                         "no": "描述明确表明没有腐烂变质",
                         "unknown": "描述不足以判断"}}},
          "state": {"description": {"$expr": "=inputs.description"}}
        },
        "decode": {"mode": "yes_no_at_least@1",
                   "thresholds": {"tau_yes": 0.8, "tau_no": 0.8}}
      },
      "returns": "Bool"
    }
  },
  "features": {"inWindow": "=inputs.hoursSinceDelivery <= params.windowHours"},
  "decisions": {"verdict": {"$expr": {
    "$default": {"$first": [
        {"when": "=not features.inWindow", "then": "OUT_OF_WINDOW"},
        {"when": "=effects.rot", "then": "SELLER_DUTY"}],
      "otherwise": "BUYER_DUTY"},
    "if_unknown": "MANUAL"}}},
  "outputs": {"verdict": {"value": "=decisions.verdict"}}
}
```

从这个例子可以看出程序的几个组成部分：

| 部分 | 例子中的内容 | 属于哪一层 |
|---|---|---|
| `inputs`、`params` | 小时数、描述；时限 48 | 输入与政策参数 |
| `effects` 中的 `$read` | 向模型提问"是否腐烂"，`jev@1` 是一种模型读取 Provider | 事实层：怎样取得事实 |
| `binding.request` | 模型、问题文本、选项说明、送给模型的材料 | 事实层：问什么、怎样问 |
| `binding.decode` | 概率达到 0.8 才判定为是或否，否则为未知 | 事实层：怎样把概率变成值 |
| `features`、`decisions` | 是否在时限内；按顺序判定 | 政策层 |
| `outputs` | 对外返回 `verdict` | 出口 |

这里有两个后面会反复出现的要点：

- **模型拿不准时，事实是"未知"，而不是"否"。** `effects.rot` 未达阈值时是 unknown。规则用 `$default … if_unknown` 把这种情况明确导向 `MANUAL`，而不是悄悄当成"没有腐烂"、判成买家责任。
- **问法、解码和规则都是程序的一部分。** 改问题文本、改阈值、改规则，都会得到一份新的候选程序。三类改动的成本不同（第 1.4 节和第 3 章说明），系统需要区别对待。

在这个例子上，系统要帮忙回答的典型问题是：

- 有一批带最终结论的历史案例，但还没有规则，能否自动得到一份规则？（从头建模）
- 现有程序在某些案例上判错了，是模型没读对"是否腐烂"，还是缺少一个事实（例如"包装破损导致汁液渗出"），还是规则顺序不对？怎样改，改完怎样确认更好？（持续改进）

## 1.3 系统的组成与两类任务

### 1.3.1 三个组成部分

| 部分 | 目录 | 职责 |
|---|---|---|
| 执行服务 | `engine/` | 校验和求值程序；调用 Provider 取得事实；解码；计算语义身份；保存和匹配读取回执。通过执行协议 `execution-rpc/2` 对外提供全部能力 |
| 分析 CLI | `cli/` | Java 命令行：取得材料、学习规则、蒸馏、诊断、配对实验、候选筛选与报告。只通过 RPC 使用执行服务 |
| Python 宿主 | `cli/iteration/` | 多轮流程：交替蒸馏（`fitting.py`）、持续改进（`iterate.py`）、从建模到验收的管线（`pipeline.py`）。调用分析 CLI 和执行服务，不自己求值 |

三者的关系在第 2 章展开。这里只需要记住一点：**程序怎样执行，只由执行服务决定**；CLI 和宿主负责数据组织、搜索、统计与报告。

### 1.3.2 两类任务

| 任务 | 起点 | 终点 | 主要入口 |
|---|---|---|---|
| 从头建模 | 输入输出合同、带标签的样本（或一份教师程序）；规则可以是空的，例如出口固定返回 `REVIEW` | 一份完整的候选程序，以及它在各数据划分上的表现 | `learn`、`distill`、`discover`；交替蒸馏宿主 `fitting.py` |
| 持续改进 | 一份已通过校验的完整程序，以及开发与选择用的案例 | 在固定门槛下被采用的新程序，以及每次修改的证据记录 | 迭代宿主 `iterate.py` |

两类任务可以通过管线 `pipeline.py` 连起来：先建模，再可选地做显式因果模型分析，再持续改进，最后在**候选冻结之后**用独立的验收数据做一次验收。

两类任务共用同一套底座：执行服务、材料与回执、预算、四态值、评价与报告格式。区别在于搜索什么：从头建模主要搜索"问哪些事实"和"怎样组合"；持续改进则在已有程序上做有边界的修改。

## 1.4 设计目标

下面七条目标是评价这套设计的标准。后续章节讨论任何取舍，都是在这些目标之间权衡。

**G1　产出可执行、可交付的完整程序。**
建模和改进的结果都是一份完整的作者 DSL：包含全部输入、外部读取的完整 Binding、规则和出口，可以直接交给执行服务运行。学习器内部用什么模型表示无关紧要，交付物始终是这份程序。

**G2　可解释。**
政策层是显式规则，事实层是可以单独查看的封闭问题。对每个案例，可以看到每个读取问了什么、模型给各选项的概率、解码出的值、每个中间定义的值，以及出口如何得出。

**G3　可审计、可复现。**
每次外部读取都留下回执（包括模型的原始答复），并有确定的测量身份。同一份程序在同样的材料上可以冻结重放，得到相同结果。任何报告里的数字，都可以追溯到具体的执行记录。

**G4　证据诚实。**
结论只覆盖证据实际支持的范围：未知不被当成否；假设的事实值不被当成实测；在训练集上分开了标签，不等于业务规律成立；搜索做完了，不等于全局最优。

**G5　成本受控。**
真实读取要花钱和时间。系统默认冻结执行，只用已有材料；真实派发必须显式授权；所有付费调用都在持久化的预算账本里先预留、后结算；结果不明的调用不自动重发。能在已有材料上完成的尝试（改规则、改解码）优先于需要新测量的尝试（改问法、新增读取）。

**G6　算法可替换。**
学习器、诊断分析、动作排序、采用策略、实验统计等都通过明确的接口接入，可以替换和对照实验。替换算法不影响执行、材料、预算和固定门槛。

**G7　结论范围明确。**
每个结果都说明自己证明了什么、没有证明什么。例如学习结果分别报告"拟合工作是否完成""在声明的空间内是否最优""导出程序与模型是否逐案一致""是否满足批准约束"，这四者互不替代。

### 1.4.1 改动的代价：目标 G5 的具体含义

目标 G5 在设计中最常见的体现，是按改动的位置区分代价（见仓库 `ITERATION.md`）：

| 改动 | 在程序中的位置 | 评估需要什么 |
|---|---|---|
| 规则、参数、出口 | `params`、`features`、`decisions`、`outputs` | 读取请求不变时，在已有材料上直接重放 |
| 解码 | `binding.decode` | 不需要新读取，用冻结的原始答复重新解码 |
| 问什么、怎样问 | `binding.request`：模型、问题文本、选项说明、送给模型的材料 | 测量身份改变，受影响的案例都要真实读取 |
| 新增一个读取 | `effects` 下的新定义 | 需要它的案例都要真实读取 |

前两类改动"免费"（只消耗计算），后两类需要新的付费测量。持续改进宿主在每轮先尝试解码修改，交替蒸馏宿主在加新观察前先重学规则，都是这条目标的直接结果。

## 1.5 非目标

明确不做的事情和要做的事情同样重要。以下各项不在本系统的范围内：

1. **不训练模型。** 没有梯度训练、软标签蒸馏、温度参数或 KL 损失。"蒸馏"在本系统中指把教师程序或历史标签压缩成显式布尔规则。模型只作为读取事实的仪器使用。
2. **不自动部署，不执行业务动作。** 单项命令只产出候选和报告；迭代宿主可以按采用策略更新"当前程序"，但不会发布、部署或提交任何业务动作。执行服务当前唯一可执行的外部交互是观测（`$read`），动作（`act`）被保留并拒绝。
3. **不认定事实真值或标签真值。** 历史标签是历史决策，系统学到的是这些决策的规律，不把标签提升为规范真值；模型复读的结果是假设，不是事实金标。
4. **不证明业务因果。** 冻结干预、配对实验、有限结构因果模型各自有明确的结论范围（第 10 章），真实业务因果识别需要额外的设计和假设，系统不自动提供。
5. **不保证全局最优或泛化。** 搜索在声明的谓词、深度和预算内进行；训练集上的拟合率不是未见材料上的准确率。
6. **不替使用方确定政策与数据。** 初始的输入输出合同、可用的 Provider、政策说明、样本的整理与划分，由使用方决定。
7. **不负责运行环境与业务接入。** 鉴权、存储、版本管理、正式部署由宿主系统负责；本仓库的本机服务只监听回环地址，适用于可信的本机调用。

## 1.6 设计原则

以下八条原则把目标落实为可检查的约束。它们是"固定门槛"，即任何可替换的算法都不能绕过的部分。

### P1　执行服务是唯一权威

CLI 和宿主不解释 DSL、不解码模型答复、不实现 Provider，也不用自己的预测代替真实执行。

- Java 侧只有入口 `Main` 选择具体的 RPC 客户端，其他流程只接收执行端口 `ExecutionSession`；依赖测试约束执行端口和协议视图不能反向引用算法。
- 学习器导出的规则必须写回完整程序，经服务编译、全批重放，再与学习器的预测逐案对齐。不一致时报告 `ALIGNMENT_FAILED`，候选不合格。

**理由**：如果分析侧有自己的求值器，它与引擎在未知值、分支合流、短路等语义上的细微差异，会让"分析认为更好的候选"在实际执行中表现不同。只认真实执行，就消除了这类偏差。

### P2　事实与政策分离

读取只问事实，不问结论；规则不能新增绕开事实读取、从原文直接推导结论的通道。

- 盲读取：Provider 收到的请求只来自 Binding，不包含案例的期望结论。
- 持续改进要求读取问题不能直接询问最终结论；编辑范围的静态检查会拒绝暴露多个最终结论标签的问题，以及新增的纯输入依赖。
- 学习时，与目标出口同名的输入不能作为特征，避免标签直接泄漏。

**理由**：政策必须可见、可审，事实必须可以独立检查。如果模型直接给出结论，事实层和政策层就重新混在一起，无法判断错误发生在哪一层。

**边界**：静态检查不能识别所有改名后的结论代理，也不能证明自然语言问题与原意等价。这一点在第 11 章和第 16 章说明。

### P3　四态值不补全

每个值有四种状态：已知（known）、缺失（absent）、未知（unknown）、错误（error）。系统在任何环节都不把后三种改成某个已知值。

- 学习只用全部谓词都已知的训练行；被排除的行逐案列出，并且仍在报告的分母里。
- 导出的程序对未知结果有显式回退（转人工，或回到原程序的出口），而不是当成否定。
- 局部修复中，适用条件未知时"这条规则不适用"，继续看下一条规则或回到原程序，而不是把条件当成假。

**理由**："没有证据"和"证据说没有"在业务上是两回事。把未知补成否，会让规则在模型拿不准时系统性地偏向某个结论，而且这种偏差在报告里看不出来。

### P4　假设不冒充回执

能修复输出的假设值、模型复读的意见、重解码的值，都必须标明来源，不能进入真实回执库，也不能当作实测改进。

- 学习、蒸馏、局部修复都拒绝案例中的外部 `facts`、供给（`supply`）和非严格回执。
- 复读结果标记为 `MODEL_REVIEW`，用于干预时标记为 `HYPOTHESIS`。
- 复用回执必须严格匹配实际测量上下文（`STRICT`）。

**理由**：如果假设能混进实测，就无法分辨一次"改进"是程序真的更好，还是某个假设恰好让结果变好。

### P5　冻结优先，成本保守

- 默认冻结执行，只使用已有回执和不需要外部读取的表达式；真实派发必须显式使用 `--live`。
- 付费调用之前在持久化账本中预留额度并写盘，完成后结算；调用超时或传输中断时记为未确认（`UNCONFIRMED`），不自动重试，并阻止后续付费调用。
- 一次任务的各阶段共享同一份总预算，阶段切换不会重新发放额度。

**理由**：模型调用结果不明时重发，可能导致重复扣费；而把不明调用当成零成本，会让预算报告失真。保守处理保证"报告的剩余额度不会多于实际剩余"。

### P6　数据角色隔离

每份数据有明确的角色，角色之间不能混用：

| 角色 | 用途 |
|---|---|
| 训练（train） | 生成候选谓词、拟合规则 |
| 开发（development） | 从头建模时：模型固定后的报告集；持续改进时：诊断、复读与提案的依据 |
| 留出（holdout） | 模型固定后的报告集 |
| 选择（selection） | 持续改进中比较和采用候选；因为会被反复使用，属于自适应调优数据 |
| 验收（acceptance） | 最终候选冻结后才读取的封存数据，结果不反馈给任何优化步骤 |

同源的案例用 `provenance.group_id` 标记，同一组不能跨划分，防止同源材料泄漏。

**理由**：一份数据一旦参与了选择，它上面的成绩就不再是对未见数据的估计。角色隔离是"成绩可信"的前提。

### P7　搜索可替换，门槛固定

学习算法、观察搜索、局部规则生成、诊断分析、动作排序、提案构造、机制指标、采用策略、实验统计，都可以替换。以下部分不可替换：

- 执行与材料：真实求值、严格回执、四态处理；
- 资源：预算预留与结算、未确认调用的阻断；
- 资格：导出对齐、批准约束、技术失败与未决输出的拦截、提取改动的新采样确认；
- 数据：角色与组隔离、封存验收的读取时机。

替代算法只能从已经通过固定门槛的候选中选择，或者放弃选择；不能放宽门槛、扩大预算或修改原始成绩。

**理由**：这样可以放心地对照实验不同的算法，而不用担心某个算法通过"降低标准"获得更好的分数。

### P8　每个结论都有范围

系统用一组互不替代的状态描述结果，避免一个笼统的"成功"：

| 状态 | 含义 | 不代表 |
|---|---|---|
| `fit_complete` | 学习器完成了它声明的拟合工作 | 找到了最优解 |
| `optimal_within_space` | 在给定谓词、深度、训练行和目标下已穷尽搜索 | 业务规则正确，或泛化最优 |
| 对齐证书 | 导出程序的实际输出与学习器预测逐案一致 | 读取正确，或机制成立 |
| `candidate_eligible` | 对齐、执行完整、批准约束均通过 | 候选比基线更好，或应当被采用 |
| `PERFECT_FIT` | 这一批训练案例的实际输出全部匹配 | 未见材料上的准确率 |

命令的退出码也遵循同样的思路：0 表示指定的工作完成，2 表示输入或合同无效，3 表示服务、读写或付费结果不明的故障，4 表示预算、材料、对齐、约束或搜索尚未完成。退出码为 0 并不表示结果达到某个质量门槛，仍需查看具体状态和指标。

## 1.7 怎样判断"做成了"

结合上面的目标和原则，一次建模或改进被认为"做成了"，需要同时满足：

1. 产出的是一份完整程序，并通过执行服务校验（G1、P1）；
2. 程序在指定案例上实际执行完整，没有技术失败和未决输出（P3、P7）；
3. 导出与预测逐案对齐，批准约束全部通过（P1、P8）；
4. 改进的依据来自真实执行，而不是假设或复读（P4）；
5. 在没有参与任何选择的独立数据上，表现达到使用方的要求（P6）。

前四条由系统自动检查。第五条需要使用方提供独立的验收数据，由管线在候选冻结后执行；交替蒸馏宿主只在训练批上工作，它的结果需要另外安排独立验收。

## 1.8 本章小结

- 系统把业务判定拆成"模型回答封闭事实问题"和"显式规则组合事实"两层，写在同一份完整程序里。
- 系统的任务是得到并持续改进这样的程序：问哪些事实、怎样问、怎样组合。
- 七条目标：完整程序、可解释、可审计、证据诚实、成本受控、算法可替换、结论范围明确。
- 七条非目标：不训练模型、不自动部署、不认定真值、不证明因果、不保证最优与泛化、不替使用方定政策、不负责运行环境。
- 八条原则构成固定门槛：执行唯一权威、事实政策分离、四态不补全、假设不冒充回执、冻结优先、数据角色隔离、搜索可替换而门槛固定、结论有范围。
